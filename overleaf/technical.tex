\chapter{Introduction}

\section{What this manual covers}

This is the complete, self-contained setup and operation manual for the
Carolus/RoboMaster S1 platform: a DJI RoboMaster S1 ground robot, rooted to
expose the RoboMaster EP SDK, carrying a Raspberry Pi~4B at the turret
position, running Carolus (also called uVGS-2) --- a 4-LED beacon
pose-estimation system --- to autonomously search for, align to, approach,
and dock at a fixed beacon.

Everything in this manual has been executed and verified on this exact
hardware. Where a step has not been physically re-verified on this specific
unit but is inherited from a documented, working precedent (e.g.\ a rooting
procedure that predates this project), that is stated explicitly at the
point it occurs.

\section{Hardware}

\begin{itemize}
  \item \textbf{Robot:} DJI RoboMaster S1, rooted via the
  \texttt{s1\_sdk\_hack\_v0.0.5} community hack, which exposes the
  RoboMaster EP SDK (chassis drive, gimbal control, onboard camera, wheel
  odometry, IMU) over a local API not officially released for the S1.
  \item \textbf{Companion computer:} Raspberry Pi~4B, mounted at the turret,
  connected to the robot over USB via RNDIS. The Pi holds the single
  connection to the robot's SDK, runs the camera/beacon-tracking node, and
  \textbf{runs Carolus itself}, so the full perception pipeline is onboard
  and the robot needs no network link to estimate its pose
  (Section~\ref{sec:where-carolus-runs}).
  \item \textbf{Lab PC:} runs the operator GUI and builds/edits the same
  Carolus code for development, but does not operate the robot with it ---
  not physically connected to the robot, communicating with the Pi over the
  local network.
  \item \textbf{Camera:} the S1's own internal camera (built into the
  gimbal/head), streamed over the SDK. This project does not use an external
  Intel RealSense D455 --- some inherited reference material describes a
  D455-based pipeline (see Chapter~\ref{ch:calibration}'s calibration
  discussion); that material is noted where it applies to calibration
  \emph{technique}, not to this robot's actual camera hardware.
\end{itemize}

\section{Software stack}

\begin{itemize}
  \item \textbf{Operating systems:} Raspberry Pi runs Ubuntu 20.04.6~LTS
  (aarch64). The lab PC runs Ubuntu 22.04.5~LTS (x86\_64) --- not the
  officially supported target for ROS Noetic, which requires local
  workarounds documented in Chapter~\ref{ch:carolus-node}.
  \item \textbf{Middleware:} ROS Noetic (1.17.4) on both machines.
  \item \textbf{Robot control:} the official \texttt{robomaster} Python SDK,
  requiring Python~3.7 specifically.
  \item \textbf{Vision:} Carolus/uVGS-2, a C++ ROS node built on OpenCV,
  Eigen3, and Ceres Solver, performing 4-LED blob detection and a
  Perspective-4-Point (P4P) pose solve.
\end{itemize}

\section{How the pieces fit together}

Three machines, one data path. The robot never talks to the lab PC directly
--- everything goes through the Pi, which holds the only SDK connection.

\begin{lstlisting}[style=shell]
  RoboMaster S1              Raspberry Pi 4B              Lab PC
  camera, chassis,   USB /   SDK bridge, Carolus,  local  launcher (GUI),
  gimbal             RNDIS   ROS master            net    development
      [ ] <-------------------> [ ] <-------------------> [ ]
   192.168.42.2            192.168.42.3  /            192.168.0.100
                           192.168.0.103
\end{lstlisting}

Inside the Pi, the pipeline is a straight line from pixels to a pose:

\begin{lstlisting}[style=shell]
  camera      blob         P4P solve      /pose        control
  frames  --> detection --> (Ceres)   --> 6-DOF    --> SEARCH / ALIGN
                 |                                     / APPROACH
                 |  4 LEDs                                  |
                 +------------------------------------------+
                        /carolus/cmd_vel  -> back to the robot
\end{lstlisting}

\texttt{rm\_cam\_beacon.py} (Chapter~\ref{ch:camera}) owns both ends --- it
publishes the frames and it is the only thing that sends motion commands to
the robot. Carolus (Chapter~\ref{ch:carolus-node}) owns the middle.

\section{What Carolus is}

Carolus (internally named uVGS-2, Unified Visual Guidance System version~2)
is a monocular pose-estimation system originally developed for NASA's
Astrobee free-flying robot aboard the International Space Station, derived
from the earlier SVGS system. It detects four illuminated beacon points
(LEDs) in a camera image, identifies which detected blob corresponds to
which known 3D point on the physical beacon, and solves a Perspective-4-Point
optimization (via Ceres Solver, not OpenCV's \texttt{solvePnP} family) to
recover the beacon's full 6-DOF pose relative to the camera.

\textbf{Carolus's camera frame follows the standard computer-vision
convention} --- $X$ right, $Y$ down, $Z$ forward --- which is
\emph{right-handed}, as is ROS's REP-103 body frame ($X$ forward, $Y$ left,
$Z$ up). Converting between them is therefore an ordinary change of basis
between two right-handed frames, and is necessarily a \emph{proper} rotation
(determinant~$+1$). Chapter~\ref{ch:tf-conversion} derives the conversion in
full and explains why the operation is a similarity transform rather than a
component-wise permutation of the quaternion's vector part.

\begin{warningbox}
\textbf{Correction, 2026-08-11.} Earlier revisions of this manual stated that
Carolus's native frame is \emph{left-handed}, and that the conversion to
REP-103 is therefore improper (determinant~$-1$). \textbf{That was wrong.}
REP-103 defines both the body frame and the camera ``\_optical'' frame it
names, and states that all its frames are right-handed; a change of basis
between two right-handed orthonormal frames is orientation-preserving by the
definition of a rotation, so determinant~$+1$ is the only possibility. The
claim is corrected here rather than quietly deleted, because a reader who saw
the earlier version may have carried the improper-conversion idea forward
into their own work.
\end{warningbox}

\section{The four operating states}

Once running, the robot's autonomous behavior is a state machine:

\begin{description}
  \item[SEARCH] The gimbal sweeps without moving the chassis, looking for
  the beacon. If not found from the current heading, the chassis rotates to
  a new heading and the gimbal sweeps again (a ``fan search'' pattern).
  \item[ALIGN] Once the beacon is detected, the chassis rotates in place
  until it faces the beacon.
  \item[APPROACH] The gimbal tracks the beacon while the chassis advances
  along the same heading.
  \item[STOP] Triggered once within a target stopping distance of the
  beacon.
\end{description}

A separate, more deliberate \textbf{docking} behavior performs a calibrated,
verified approach-and-stop sequence rather than the lighter continuous
SEARCH/ALIGN/APPROACH loop (Section~\ref{sec:docking}).

\chapter{Quick Start --- A Typical Session}
\label{ch:quickstart}

\runson{the \textbf{lab PC} (the launcher and these commands), driving the
\textbf{Raspberry Pi} over SSH. The robot must be powered on.}

\textbf{This chapter is for a machine that is already set up.} If you are

\section{The five-minute version}

\begin{enumerate}
  \item \textbf{Power on the robot} --- listen for \textbf{two chimes}, not
  one (Chapter~\ref{ch:poweron}). One chime means the root hack is not
  active and nothing below will work.
  \item \textbf{Power on the Pi} with the button on the UPS HAT
  (Section~\ref{sec:pi-power} --- the HAT's port, not the Pi's).
  \item \textbf{Bring up the RNDIS link}, on the Pi. It does not survive a
  reboot, so this is needed every session (Chapter~\ref{ch:network}):
\begin{lstlisting}[style=shell]
sudo ip link set eth1 up
sudo ip addr add 192.168.42.3/24 dev eth1
ping -c 4 192.168.42.2        # the robot -- expect 0% loss
\end{lstlisting}
  \item \textbf{Start the launcher}, on the lab PC:
\begin{lstlisting}[style=shell]
python3 shortcuts/carolus_launcher.py
\end{lstlisting}
  \item \textbf{Click the tabs in order} (Chapter~\ref{ch:launcher}): T1,
  then T2, then T3. Each one waits for the previous.
\end{enumerate}

That is a working stack: camera streaming, Carolus solving poses, the robot
drivable from the keyboard.

\section{Without the launcher, by hand}

Useful when debugging, or when the launcher itself is the suspect. Three
separate SSH shells to the Pi, in this order --- each needs its own
\texttt{ROS\_MASTER\_URI}/\texttt{ROS\_IP}, they are per-shell:

\begin{lstlisting}[style=shell]
# --- Shell 1, on the Pi: the ROS master ---
source /opt/ros/noetic/setup.bash
export ROS_MASTER_URI=http://192.168.0.103:11311
export ROS_IP=192.168.0.103
roscore

# --- Shell 2, on the Pi: the camera + SDK bridge (Chapter 6) ---
source /opt/ros/noetic/setup.bash
export ROS_MASTER_URI=http://192.168.0.103:11311
export ROS_IP=192.168.0.103
source ~/Python-3.7.17/env/bin/activate
python3.7 carolus_ws/src/robomaster_cam/scripts/rm_cam_beacon.py

# --- Shell 3, on the Pi: Carolus itself (Chapter 8) ---
source /opt/ros/noetic/setup.bash
export ROS_MASTER_URI=http://192.168.0.103:11311
export ROS_IP=192.168.0.103
source ~/carolus_ws/devel/setup.bash
roslaunch carolus_node testcarolus.launch ubuntu2204_preload:=false
\end{lstlisting}

\section{Is it working? Three checks from the lab PC}

Run these on the \textbf{lab PC}, not the Pi --- that is the whole point:
they confirm the nodes are visible across the network, not just locally.

\begin{lstlisting}[style=shell]
export ROS_MASTER_URI=http://192.168.0.103:11311
export ROS_IP=192.168.0.100

rostopic hz /camera/color/image_raw   # expect ~16-30 Hz
rostopic hz /pose                     # ~13 Hz, ONLY with a beacon in view
rosnode list                          # expect /ep_camera_beacon_follower
\end{lstlisting}

\textbf{If \texttt{rostopic} finds nothing while the Pi says the node is
running}, the cause is almost always a missing
\texttt{ROS\_MASTER\_URI}/\texttt{ROS\_IP} in the shell that launched it ---
\texttt{rospy} then falls back to \texttt{localhost} and the node is
invisible from anywhere else.

\section{Shutting down}

Close the launcher --- it kills its own remote processes and verifies they
died. By hand, on the Pi, the bracket in each pattern is not optional (see
Chapter~\ref{ch:launcher}):

\begin{lstlisting}[style=shell]
pkill -f "[r]m_cam_beacon"
pkill -f "[r]oscore"; pkill -f "[r]osmaster"
pgrep -af "roscore|rosmaster|rm_cam_beacon"   # confirm nothing is left
\end{lstlisting}

\textbf{Always confirm the bridge is dead before the next session.} An
orphaned \texttt{rm\_cam\_beacon.py} keeps the robot's single SDK connection
open, and the next launch then hits the double-connection failure ---
motion commands stop working with no error shown
(Chapter~\ref{ch:camera}).

\chapter{Powering On the Robot}
\label{ch:poweron}

\runson{the \textbf{robot itself} (physical handling). The Raspberry Pi and lab PC are not involved until Chapter~\ref{ch:raspberrypi}.}

\section{Before you start}

\begin{itemize}
  \item The S1's smart battery, charged. Charging is required before first
  use even if the battery shows some charge --- this ``wakes up'' the
  battery.
  \item The S1 charger, plugged into mains (100--240\,V, 50/60\,Hz). A full
  charge takes approximately 1\,h30.
  \item The battery only charges between 5\,\textdegree C and
  45\,\textdegree C.
  \item Do not touch the motors, motor mounting plate, or the inside of the
  Mecanum wheels immediately after powering the robot off --- they can be
  hot.
  \item Do not attempt to charge a battery that has dropped below 1\,V per
  cell; this poses a fire risk.
  \item Use the official DJI charger only.
\end{itemize}

\section{Power-on sequence}

The battery compartment is behind the chassis's rear armor panel, so the
sequence is: open, insert, power on, close.

\begin{enumerate}
  \item Press the rear armor release button to open the chassis's rear
  cover.
  \item Insert the smart battery into its compartment, making sure it is
  firmly seated --- a poorly seated battery gives poor contact and can cause
  the robot to lose battery information.
  \item Press and hold the power button (on the battery itself) for more
  than two seconds to power on.
  \item Close the chassis's rear armor.
\end{enumerate}

The Raspberry Pi at the turret is a separate power domain from the robot
chassis; there is no required power-on order between the two, and the
USB/RNDIS cable connecting them is for the SDK link (Chapter~\ref{ch:network}),
not for powering either device.

\section{Confirming the robot is powered on}

Expected light signals at power-on:

\begin{itemize}
  \item \textbf{Gimbal (head) LED:} blinks cyan, counterclockwise.
  \item \textbf{Chassis LED:} solid cyan.
  \item \textbf{Motion controller LED:} blinks blue slowly --- this means
  the motion controller is working normally.
\end{itemize}

\section{Confirming the robot is rooted}

This project assumes a rooted S1 exposing the RoboMaster EP SDK. Without the
root hack (Chapter~\ref{ch:rooting}), SDK commands (chassis, gimbal, camera)
will not respond, even though the robot otherwise powers on and behaves
normally through the stock RoboMaster app.

\textbf{Audible cue at boot:} a correctly rooted S1 emits two chimes instead
of the usual single chime. The hack persists across power cycles --- it does
not need to be reapplied every time the robot is powered on.

\textbf{Concrete test, once the Pi is connected over RNDIS
(Chapter~\ref{ch:network}):} the camera/beacon node
(\texttt{rm\_cam\_beacon.py}, Chapter~\ref{ch:camera}) opens the one and
only SDK connection this project uses:

\begin{lstlisting}[style=code]
self.ep = robot.Robot()
self.ep.initialize(conn_type="rndis")
\end{lstlisting}

\begin{itemize}
  \item \textbf{Success:} the node's log shows the connection succeeding, and
  the robot responds to \texttt{Twist} commands published on
  \texttt{/carolus/cmd\_vel} (Chapter~\ref{ch:camera}).
  \item \textbf{Failure:} the SDK connection fails or times out. First
  confirm the network link itself (\texttt{ping 192.168.42.2} from the Pi,
  Chapter~\ref{ch:network}). If the network link is fine but the SDK
  connection still fails, redo the power-on and listen carefully for the
  double chime --- a single chime means the root hack is not active.
\end{itemize}

\textbf{Do not use any script other than \texttt{rm\_cam\_beacon.py} to test
this.} Two independent scripts each attempting
\texttt{ep.initialize(conn\_type="rndis")} at the same time silently blocks
robot motion after a few commands, with no error surfaced --- this failure
mode is why this project uses exactly one script holding the SDK connection
at any time (see Chapter~\ref{ch:camera}).

\section{Which camera is mounted}

This project uses the S1's own internal camera, not an external Intel
RealSense D455. Physically: a D455 is an external rectangular camera housing
mounted in addition to the robot's own head; if there is no such external
camera, the internal camera is in use. In software, once
\texttt{rm\_cam\_beacon.py} is running (Chapter~\ref{ch:camera}), the
internal camera feed appears on \texttt{/camera/color/image\_raw}
immediately, with no separate D455 driver (\texttt{rs\_camera.launch})
needed.

\label{ch:rooting}

\runson{a \textbf{Windows or macOS computer} connected to the robot by micro-USB. Not the Raspberry Pi, not the Ubuntu lab PC --- the RoboMaster app required for this step does not run on Linux.}

If Chapter~\ref{ch:poweron}'s double-chime check already confirmed the robot

\section{What the hack does}

DJI's RoboMaster app exposes a limited, sandboxed Python scripting
environment (``the Lab''). The S1's Python subsystem runs with root
privileges internally, but DJI restricts which modules a Lab script can
import via a whitelist attached to the \texttt{\_\_builtins\_\_} object.
Several of the whitelisted modules (needed for legitimate scripting
features) still hold a reference to the real, unrestricted
\texttt{\_\_builtins\_\_} internally. That reference can be recovered and
used to import \texttt{subprocess}, which can then invoke a shell script
already present on the robot's filesystem (\texttt{adb\_en.sh}) to enable
\texttt{adb} and open a root shell over USB.

Once a root shell is available, a patch is pushed to the robot's filesystem
that installs the RoboMaster EP SDK's full command set (the EP is DJI's
higher-end sibling to the S1; underneath, the two share nearly identical
firmware) onto the S1, which DJI has never officially released to S1 owners.

\textbf{Warning, carried over from the hack's own documentation, to be taken
literally:} this has the potential to break the robot. It did not break this
project's unit, but there is no guarantee for any given unit.

\section{Step-by-step procedure}

\subsection{What you need}

\begin{itemize}
  \item A computer running Windows or macOS (the RoboMaster app requires
  one of these to configure the S1; the Raspberry Pi is not involved in this
  chapter).
  \item Android SDK Platform-Tools (\texttt{adb.exe} and friends) --- unzip
  anywhere, remember the path.
  \item A micro-USB cable.
  \item The RoboMaster app, with a DJI account.
\end{itemize}

\subsection{Procedure}

\begin{enumerate}
  \item Connect the computer to the S1's Intelligent Controller Micro-USB
  port with the micro-USB cable. Ensure no other Android device is connected
  over USB during this procedure.

  \item Power on the robot (Chapter~\ref{ch:poweron}) and connect the
  RoboMaster app to it via its own Wi-Fi hotspot (visible on top of the
  gimbal, with a password shown alongside it).

  \item In the app: \textbf{Lab} $\to$ \textbf{DIY Programming} $\to$ select
  \textbf{Python} on the top bar $\to$ \textbf{New} to create a new program.

  \item Paste the following into the program editor exactly. This is the
  current, working root script for this hack version --- do not use an
  older variant that imports \texttt{'subprocess'} as a literal string or
  reads from \texttt{rm\_log} instead of \texttt{rm\_define}; a firmware
  update closed that specific path.

\begin{lstlisting}[style=code,language=Python]
def root_me(module):
    __import__=rm_define.__dict__['__builtins__']['__import__']
    return __import__(module,globals(),locals(),[],0)

builtins=root_me('builtins')
x=root_me('sub'+'process')
proc=x.Popen('/system/bin/adb_en.sh',shell=True,executable='/system/bin/sh',
             stdout=x.PIPE,stderr=x.PIPE)
\end{lstlisting}

  \item Run the program from within the Lab. A correct run shows no
  compilation errors and the console prints \texttt{Execution Complete}. Do
  not close the RoboMaster app.

  \item On the computer, open a terminal in the folder containing the
  Android Platform-Tools and run:

\begin{lstlisting}[style=shell]
adb devices
\end{lstlisting}

  The S1 should appear in the device list.

  \item Confirm root access:

\begin{lstlisting}[style=shell]
adb shell
\end{lstlisting}

  \item With the root shell open, from a second terminal, in the folder
  containing the hack's distribution files (\texttt{dji\_scratch},
  \texttt{dji.json}, \texttt{dji\_hdvt\_uav}, \texttt{dji\_sys},
  \texttt{patch.sh}), push the patch:

\begin{lstlisting}[style=shell]
adb shell rm -rf /data/dji_scratch
adb push dji_scratch /data/.
adb push dji.json /data/.
adb push dji_hdvt_uav /data/.
adb push dji_sys /data/.
adb shell chmod 755 /data/dji_hdvt_uav
adb shell chmod 755 /data/dji_sys
adb push patch.sh /data/.
\end{lstlisting}

  \item Restart the S1 fully (hold the power button until it turns off,
  then hold it again to turn back on). On boot, listen for \textbf{two
  chimes instead of one} --- this confirms the hack is active
  (Chapter~\ref{ch:poweron}'s check).

  \item Close the RoboMaster app and power off the robot; the setup for
  this chapter is complete.
\end{enumerate}

\section{A pitfall to know before rooting}

Starting with hack version 0.0.3, \texttt{adb} is re-enabled by default in
the patch, which \textbf{disables RNDIS support} --- the exact link this
project's Pi$\leftrightarrow$robot connection depends on
(Chapter~\ref{ch:network}). If RNDIS stops working after rooting, comment
out the \texttt{adb} line in \texttt{patch.sh} before pushing the patch, or
re-push a corrected \texttt{patch.sh} and restart the robot again.

\section{Powering the Pi --- two USB-C ports, only one of them right}
\label{sec:pi-power}

\begin{warningbox}
\textbf{Read this before plugging anything in.} The Pi carries a UPS HAT (a
green PCB underneath it, with its own battery and a physical ON/OFF button
on the back). That means \textbf{two different USB-C ports}, which look
interchangeable and are not:

\begin{itemize}
  \item \textbf{The HAT's USB-C port} (on the green PCB underneath) ---
  \textbf{this is the one to use.} It charges the internal battery, a blue
  ``Charge'' LED lights up, the ON/OFF button works, and the Pi then runs
  standalone on battery.
  \item \textbf{The Pi's own POWER IN port} (on the Pi board itself, to the
  left of the HDMI connectors) --- powers the Pi directly. It boots, but the
  HAT's ON/OFF button is ignored and the Pi is tethered to the cable. Not
  for normal sessions.
\end{itemize}

\textbf{If the Pi will not turn on:} check the cable is on the HAT port and
not the Pi's POWER IN, and that the charge LED is blue. This is the single
most common physical blocker on this setup.
\end{warningbox}

\textbf{Normal routine:} plug the charger into the HAT port the evening
before a session. The next day the Pi runs on its own battery, started and
stopped with the physical button --- no cable, no tether.

\chapter{Network Setup (RNDIS)}
\label{ch:network}

\runson{the \textbf{Raspberry Pi} for the interface commands; one step at the end runs on the \textbf{lab PC} and is marked as such.}

The robot exposes an RNDIS virtual Ethernet interface over the same USB
cable used for the SDK connection. The robot holds a fixed address,
\texttt{192.168.42.2}; the Raspberry Pi must be configured on the same
subnet.

\section{Bringing up the link}

\textbf{Run these two commands at the start of every session, on the Pi.}
The interface does not persist across Pi reboots --- this is expected
behavior on this hardware, not a fault, and there is no step elsewhere in
this manual that avoids needing it.

\begin{lstlisting}[style=shell]
sudo ip link set eth1 up
sudo ip addr add 192.168.42.3/24 dev eth1
\end{lstlisting}

If the interface is not named \texttt{eth1} on your system, identify it
first:

\begin{lstlisting}[style=shell]
ip -br addr
# look for eth1 / usb0 / enx<MAC> -- whichever one is meant to carry 192.168.42.x
\end{lstlisting}

\textbf{Never assign \texttt{192.168.42.2} to the Pi} --- that address
belongs to the robot.

\subsection{If you intend to automate this over SSH}

Typing the two commands by hand prompts for a password, which is fine
interactively. \textbf{Any script that brings the interface up over SSH needs
passwordless \texttt{sudo} on the Pi}, otherwise it hangs silently waiting
for a prompt it cannot display --- the process simply appears frozen, with no
error. Check before automating anything:

\begin{lstlisting}[style=shell]
ssh <user>@<pi> 'sudo -n true && echo "passwordless sudo OK"'
\end{lstlisting}

If it fails, grant it with \texttt{visudo} on the Pi (scope it to the two
\texttt{ip} commands rather than granting blanket rights).

\section{Verifying the link}

\begin{lstlisting}[style=shell]
ping -c 4 192.168.42.2
\end{lstlisting}

Expect 0\% packet loss, sub-millisecond round-trip time once the interface
is correctly up.

\section{A quick automated alternative}

Rather than typing the two commands above by hand every session, they can be
scripted:

\begin{lstlisting}[style=shell]
sudo ip link set eth1 up && sudo dhclient eth1
\end{lstlisting}

This project's own operator tooling (not covered in this manual) runs the
equivalent of the first two-command form automatically as part of its first
launch step, over SSH from the lab PC.

\section{Lab PC hostname resolution}

If any ROS tool on the lab PC (e.g.\ \texttt{rqt\_image\_view}) shows a
black image or errors with something like
\texttt{Couldn't find AF\_INET address for [ubuntu]}, add the Pi's hostname
to \texttt{/etc/hosts} on the lab PC:

\begin{lstlisting}[style=shell]
echo "192.168.0.103 ubuntu" | sudo tee -a /etc/hosts
\end{lstlisting}

Unlike the RNDIS interface on the Pi, this fix is permanent on the lab PC
and does not need to be repeated.

\chapter{The Camera and Robot Bridge}
\label{ch:camera}

\runson{the \textbf{Raspberry Pi} --- this is the only machine that ever connects to the robot SDK. The verification commands at the end run from the \textbf{lab PC}.}

\section{Design: a single SDK connection}

The Pi runs exactly one script that ever connects to the robot's SDK:
\texttt{rm\_cam\_beacon.py} (in
\texttt{carolus\_ws/src/robomaster\_cam/scripts/}). It is not just a camera
capture script --- it is this project's single bridge to the entire SDK:
camera stream, chassis drive, gimbal control, odometry, and the IMU
subscription all go through this one script and its one connection.

\textbf{This is a deliberate design choice, not an incidental one.} Two
independent scripts each holding their own
\texttt{ep.initialize(conn\_type="rndis")} connection at the same time
silently blocks robot motion commands after a few calls, with no error
surfaced. \textbf{Never run any other script that calls
\texttt{robot.Robot().initialize(...)} while \texttt{rm\_cam\_beacon.py} is
running.}

\section{Starting the bridge}

On the Pi, with the RNDIS link up (Chapter~\ref{ch:network}) and the Python
3.7 virtual environment active (Chapter~\ref{ch:raspberrypi}). The ROS
master runs on the Pi itself (Section~\ref{sec:where-carolus-runs}), so
\texttt{ROS\_MASTER\_URI} and \texttt{ROS\_IP} must both point at the Pi's
own address on the lab network, \texttt{192.168.0.103}
(Chapter~\ref{ch:network}) --- without them \texttt{rospy} falls back to
\texttt{localhost} and the node is invisible to every other machine:

\begin{lstlisting}[style=shell]
source /opt/ros/noetic/setup.bash
export ROS_MASTER_URI=http://192.168.0.103:11311
export ROS_IP=192.168.0.103
source ~/Python-3.7.17/env/bin/activate
python3.7 carolus_ws/src/robomaster_cam/scripts/rm_cam_beacon.py
\end{lstlisting}

Source ROS \emph{before} activating the venv, in the same shell: the venv
only prepends its own \texttt{bin/} to \texttt{PATH}, it does not clear the
ROS environment variables sourced ahead of it.

In normal operation this is launched automatically by this project's own
operator tooling (the Tkinter launcher in \texttt{shortcuts/}, documented in
\texttt{shortcuts/README.md} in the repository), over SSH from the lab PC
--- it is not usually started by hand.

\section{What it connects to}

\begin{lstlisting}[style=code,language=Python]
self.ep = robot.Robot()
self.ep.initialize(conn_type="rndis")
self.chassis = self.ep.chassis
self.gimbal  = self.ep.gimbal
self.cam     = self.ep.camera
self.cam.start_video_stream(display=False)
\end{lstlisting}

From there it subscribes to the SDK's own push-data channels
(\texttt{sub\_position}, \texttt{sub\_attitude}, \texttt{sub\_velocity},
\texttt{sub\_imu}, \texttt{sub\_angle} for the gimbal), converts each
callback into a ROS message, and publishes:

\begin{center}
\begin{tabular}{ll}
\toprule
Topic & Content \\
\midrule
\texttt{/camera/color/image\_raw} & Camera frames (\texttt{sensor\_msgs/Image}) \\
\texttt{/odom} & Wheel odometry, republished from the SDK \\
\texttt{/imu} & Raw IMU, 50\,Hz requested --- \textbf{units: see warning} \\
\texttt{/carolus/gimbal\_yaw\_rel} & Gimbal yaw relative to the chassis \\
\texttt{/carolus/gimbal\_yaw\_ground} & Gimbal yaw in the world frame (absolute) \\
\bottomrule
\end{tabular}
\end{center}

\begin{warningbox}
\textbf{\texttt{/imu} units are \emph{g}, not m/s\textsuperscript{2}
(measured 2026-08-04).} At rest on a flat floor, this topic reports
\texttt{linear\_acceleration.z = -1.00664}. The SDK returns accelerations in
\emph{g}, and \texttt{rm\_cam\_beacon.py} republishes them unconverted ---
whereas \texttt{sensor\_msgs/Imu} mandates
m/s\textsuperscript{2}. Any consumer of this topic therefore sees
accelerations $9.81\times$ too small under a message contract that says
otherwise, and neither Kalibr nor MINS will detect it. The sign is also
suspect: a REP-103 $z$-up frame at rest should read $+9.81$, not $-1.0$\,g.
Gyroscope units and axis signs are likewise unconfirmed --- a reading at rest
cannot distinguish rad/s from \textdegree/s when the true rate is zero.

\textbf{Before using this topic}, verify on your own robot: gravity should
read $\approx\!9.81$ on exactly one axis at rest, and a known slow rotation
should give the expected sign and magnitude on the corresponding gyro axis.
Fix scale, sign and gyro units together --- correcting the scale alone yields
a topic that looks right while its frame convention is still unverified.

Two further constraints: this SDK accepts only 1, 5, 10, 20 and 50\,Hz for
this subscription, so 50\,Hz is the ceiling --- below the 200--500\,Hz that
camera--IMU calibration tools such as Kalibr
(Chapter~\ref{ch:calibration}) normally expect. The frequency is exposed as
the \texttt{RM\_IMU\_FREQ} environment variable so the other legal values can
be tried without editing the script.
\end{warningbox}

\begin{warningbox}
\textbf{If \texttt{/imu} is silent, check the publisher creation order
before suspecting the robot.} Every ROS publisher written to from an SDK
callback must be created \emph{before} the corresponding
\texttt{sub\_*} subscription. The robot begins pushing data the moment the
subscription is registered, and on the SDK build used here the callback runs
directly in the DDS dispatcher thread: an \texttt{AttributeError} on a
not-yet-created publisher kills that thread, after which \emph{no} telemetry
callback ever runs again. The symptom is indistinguishable from a robot that
sends nothing --- the topic is advertised, \texttt{sub\_imu} returns
\texttt{True}, and ROS logs nothing. This cost a full session to diagnose.
\end{warningbox}

and subscribes to a small set of control topics used by this project's own
higher-level tooling (not covered in this manual):
\texttt{/pose} (Carolus's own output, consumed here to drive autonomous
behavior), \texttt{/carolus/mode}, \texttt{/carolus/cmd\_vel},
\texttt{/carolus/gimbal\_vel}, \texttt{/carolus/wheels},
\texttt{/carolus/gimbal\_lock}, \texttt{/carolus/gimbal\_lock\_period}, and
\texttt{/carolus/gimbal\_recenter}.

\section{Gimbal yaw: two signals, two different meanings}

\texttt{/carolus/gimbal\_yaw\_rel} and \texttt{/carolus/gimbal\_yaw\_ground}
are not interchangeable, and confusing them is a documented source of bugs
in this project's history:

\begin{itemize}
  \item \textbf{\texttt{gimbal\_yaw\_ground}} is the gimbal's heading in the
  world frame. The S1's gimbal is yaw-stabilized: when the chassis rotates
  without an explicit gimbal command, the gimbal holds its absolute heading.
  This value stays essentially constant across a chassis rotation.
  \item \textbf{\texttt{gimbal\_yaw\_rel}} is the gimbal's angle
  \emph{relative to the chassis}. Because the gimbal holds its world heading
  while the chassis turns underneath it, this value \emph{absorbs} the
  chassis's rotation --- it is not a stable ``how far off is the beacon''
  signal across a chassis maneuver, it is a signal that actively tracks how
  much the chassis has turned since the gimbal last held still relative to
  it.
\end{itemize}

Use \texttt{gimbal\_yaw\_ground} when you need to know the camera's absolute
heading in the world. Use \texttt{gimbal\_yaw\_rel} only for what it
actually is: the angle between the gimbal and the chassis at this instant,
not a proxy for beacon bearing across a chassis rotation.

\section{Recommended method: a checkerboard with the MATLAB Camera
Calibration Toolbox}

This procedure has not yet been run against this project's own camera ---
the values in the previous section are what is actually loaded today. It is
included here as the recommended path for whoever runs the next
calibration, based on a direct comparison against Kalibr on a comparable
camera (Section~\ref{sec:kalibr-alt}).

\begin{enumerate}
  \item Print a checkerboard target with known square size (25\,mm squares
  is a proven working size for this class of camera).
  \item Capture a set of images of the board with the robot's camera
  (Chapter~\ref{ch:camera}) using \texttt{shortcuts/capture\_checkerboard.py}
  (run on the lab PC; it subscribes to \texttt{/camera/color/image\_raw} over
  the network and saves a PNG on each keypress): at least 10 images, 15 or
  more for better accuracy. The board should occupy roughly 20--25\% of the
  frame area, and be tilted more than 45\textdegree{} from the camera's
  optical axis in each shot to avoid detection errors. Capture from a wide
  variety of positions and orientations across the field of view.
  \item In MATLAB: open the \textbf{Camera Calibration app} (Apps tab), add
  the captured images, select the checkerboard pattern with the correct
  square size, and enable \textbf{tangential distortion} and \textbf{three
  radial distortion coefficients} (this camera class shows moderate
  wide-angle distortion that the default two-coefficient model under-fits).
  \textbf{Requires the Computer Vision Toolbox} --- checked directly
  (\texttt{2026-08-11}, this lab PC's desktop MATLAB R2025b): the app and
  its underlying functions (\texttt{cameraCalibrator},
  \texttt{estimateCameraParameters}, \texttt{detectCheckerboardPoints}) are
  not present by default even with a valid MATLAB licence covering the
  toolbox; install it once via Home~$\to$~Add-Ons~$\to$~Get Add-Ons if the
  app does not appear. MATLAB Online comes with every toolbox already
  provisioned and needs no such install.
  \item Run the calibration. Export the resulting coefficients to the MATLAB
  workspace and generate the calibration script --- this script contains the
  intrinsic matrix, distortion coefficients, and reprojection errors in a
  form that can be transcribed directly into \texttt{testcarolus.launch}'s
  \texttt{fx}/\texttt{fy}/\texttt{cx}/\texttt{cy}/\texttt{distortion}
  parameters (Chapter~\ref{ch:carolus-node}).
\end{enumerate}

\section{Known limitation: no confirmed auto-exposure control}
\label{sec:no-auto-exposure-control}

Two independent prior integrations of Carolus on other robots (a Leo Rover
and a Limo, both using standard UVC/V4L2-accessible cameras) report the same
failure mode: camera auto-exposure drifting while the robot moves biases
every pose Carolus reports, because the beacon-detection threshold
(Section~\ref{sec:beacon-params}) is tuned for one brightness level. One of the
two integrations spent real effort misattributing the resulting trajectory
distortion to lens/fisheye distortion before finding the actual cause. Both
fixed it by disabling auto-exposure and locking a fixed exposure time at the
OS/driver level.

\textbf{This project's camera does not offer a confirmed equivalent.} The
\texttt{robomaster} Python package this project's code actually calls
(\texttt{rm\_cam\_beacon.py}) exposes no exposure control of any kind ---
checked directly against the installed package source, not assumed. Unlike
the two prior integrations, this camera is not a plain V4L2/UVC device the
Pi can address directly; it is delivered through DJI's own SDK protocol. The
rooted SDK's own protocol tables do list one lower-level command
(\texttt{camera.exposure}, four discrete bias levels, no way to read the
current value back), reachable only through the separate on-robot Scratch
API layer, not confirmed reachable from the SDK connection this project's
code holds --- and even if it were, it biases auto-exposure rather than
disabling it, which is a different capability from what fixed the problem
for the two prior integrations.

\textbf{Practical consequence.} Auto-exposure drift while the robot moves is
a plausible, currently unquantified contributor to beacon-detection
instability on this platform. It has not been measured here. If Carolus's
pose grows visibly less reliable during motion than at rest, this is a
candidate cause worth checking before assuming a geometric or software
explanation --- the same trap one of the two prior integrations fell into.

\section{Alternative / complementary method: Kalibr}
\label{sec:kalibr-alt}

Kalibr (ETH Zürich) is the standard tool if a camera--IMU joint calibration
is needed (required for any future MINS/visual-inertial integration, not
needed for Carolus's own pose estimation, which does not use the IMU).

\textbf{Not executed here.} The camera--IMU half of this procedure has never
been run on this robot. The camera-only calibration below is unaffected and
is the part that matters for Carolus. Two constraints to know before planning
a camera--IMU session on this platform: the SDK caps the IMU subscription at
50\,Hz, well below the 200--500\,Hz Kalibr expects for a well-conditioned
solution; and \texttt{/imu} publishes accelerations in \emph{g} rather than
the m/s\textsuperscript{2} the message type mandates
(Chapter~\ref{ch:camera}), with gyroscope units and axis signs still
unconfirmed. Correct the units and verify the frame first --- Kalibr will not
detect either error, and every noise parameter it produces would be wrong by
the same silent factor.

\subsection{Target}

A $6\times6$ AprilGrid, tag size $0.089\,\mathrm{m}$, tag spacing $0.3\times$
tag size (an $\sim\!0.8\times0.8\,\mathrm{m}$ printed board). Measure the
actual printed square size and use the measured value, not the nominal one
--- even a $\sim\!1\%$ sizing error biases the recovered scale.

\begin{lstlisting}[style=code]
target_type: 'aprilgrid'
tagCols: 6
tagRows: 6
tagSize: 0.089        # metres -- MEASURE your own printed board
tagSpacing: 0.3        # ratio of gap to tag size
codeOffset: 0
\end{lstlisting}

\subsection{Installing Kalibr}

\textbf{Do not separately clone \texttt{numpy\_eigen} or

\begin{lstlisting}[style=shell]

\end{lstlisting}

and if it fails, remove any independently-cloned copy of
\texttt{Schweizer-Messer}, then rebuild:

\begin{lstlisting}[style=shell]
rm -rf build/ devel/ install/
catkin_make -DCMAKE_BUILD_TYPE=Release
\end{lstlisting}

\subsection{Capturing data and running the calibration}

Record a rosbag while moving the camera (or the robot itself, for a joint
camera--IMU calibration) through the AprilGrid's field of view for 60--90
seconds, exciting all six degrees of freedom (translate near/far/side to
side, rotate about all three axes, not just yaw).

\begin{lstlisting}[style=shell]
rosbag record -O calib_data.bag /camera/color/image_raw
\end{lstlisting}

Run the calibration:

\begin{lstlisting}[style=shell]
export KALIBR_MANUAL_FOCAL_LENGTH_INIT=1
kalibr_calibrate_cameras \
    --bag calib_data.bag --target target.yaml \
    --models pinhole-radtan \
    --topics /camera/color/image_raw \
    --approx-sync 0.01
\end{lstlisting}

If Kalibr reports \texttt{Initialization of focal length failed}, provide a
manual seed value (\texttt{600} is a reasonable starting guess for a
$640\times480$-class image; scale proportionally for other resolutions).

\subsection{Reading the result}

Kalibr writes three files: a \texttt{.txt} summary, a \texttt{.pdf} of
reprojection-error plots, and a \texttt{.yaml} with the calibration
parameters. \textbf{Target: reprojection error under 0.2--0.5 pixels.} In
practice, a completed run can land a little outside that target (observed:
0.59--0.67\,px std on a comparable camera) without necessarily being
unusable --- treat the target as a goal to aim for, not a hard pass/fail
gate, and judge the calibration by whether downstream pose estimates are
stable and physically plausible.

\section{Camera--IMU time offset}

If a Kalibr camera--IMU joint calibration is run, its output
\texttt{timeshift\_cam\_imu} is in \textbf{seconds}, with the convention
$t_{\mathrm{imu}} = t_{\mathrm{cam}} + \mathrm{shift}$. This matches
OpenVINS's own internal convention exactly --- the value can be used
directly with no sign flip if it is later consumed by an OpenVINS-based
filter.

\runson{\textbf{the Raspberry Pi 4B} for actually running Carolus --- this

\section{Where Carolus runs}
\label{sec:where-carolus-runs}

\subsection{A note on visual-inertial navigation}

MINS has been run on this Raspberry Pi, both on its own simulation and on
data recorded from this robot. It builds on \texttt{aarch64} and produces a \emph{consistent}
estimate on the simulation (RMSE 0.113\textdegree{} / 0.082\,m, NEES 0.9 and
1.4), with no divergence, at \textbf{0.3--0.4$\times$ real time} --- under a
sensor load far heavier than this robot's (IMU at 200\,Hz, \emph{two}
cameras, and a LIDAR).

On a 60\,s recording of \emph{this} robot's \texttt{/imu} and
\texttt{/camera/color/image\_raw}, it processed the whole bag at
\textbf{0.7$\times$ real time}: CAM 118\,ms, IMU 3\,ms, 122\,ms of compute
per 88\,ms of data. So \textbf{``MINS does not run on a Raspberry Pi'' is not
correct} --- it runs, on this robot's own data. What is correct is that
\textbf{it does not reach real time here}, even with one camera, no LIDAR and
a 50\,Hz IMU, and that essentially all of the cost is the camera update. The
0.7$\times$ is also optimistic: \texttt{rosbag record} throttled the sources
to 16\,Hz of camera against 30\,Hz live.

\textbf{Two practical points if you repeat this.} MINS's live-subscribe entry
point is \textbf{ROS 2 only} --- in \texttt{run\_subscribe.cpp} the
\texttt{ROS\_AVAILABLE == 1} branch contains two \texttt{\#include} lines and
nothing else, so under ROS Noetic the binary initialises, subscribes to
nothing, and exits immediately even with data flowing. Use the \texttt{bag}
binary and a recorded rosbag, which is the path \texttt{subscribe.launch}'s
own hard-wired \texttt{rosbag play} node implies. And do not quote pose
accuracy from such a run unless the camera--IMU extrinsic has been
calibrated and the IMU units corrected (Chapter~\ref{ch:camera}) --- with a
placeholder extrinsic and accelerations in \emph{g}, the filter diverges
grossly while the timing figures stay valid.

\subsection{MINS on the ground station (lab PC)}
\label{sec:mins-ground-station}

\textbf{MINS's deployment target is the lab PC, not the Pi.} The relocalisation
work this manual builds towards fuses MINS with Carolus on a ground station
that receives the robot's data over the network, not on board the robot
itself --- the Pi build above remains useful (it is inside MINS's own tested
OS/ROS combination, Section~\ref{sec:where-carolus-runs}) but is a secondary
path, not the one this section documents.

MINS is built in its own catkin workspace on the lab PC
(\texttt{mins\_sandbox/}), kept entirely separate from the workspace this
manual otherwise describes --- nothing under \texttt{carolus\_ws} depends on
it, and nothing here should be built alongside the main pipeline. This is
also separate from the \texttt{T6 MINS (simulation, Pi)} launcher button
(Section~\ref{sec:launcher-tabs}), which runs MINS's own bundled simulation
demo on the Pi's \texttt{\textasciitilde{}/mins\_sandbox\_ws} and is
unaffected by anything in this section --- both are real, both are
separate MINS installs for separate purposes, and neither depends on the
other.

\textbf{Verified 2026-08-11: the workspace builds cleanly, and the
camera-image boundary has been tested against real data, not only compiled.}
Three fixes were needed on this exact machine (Ubuntu 22.04.5) that a
20.04/Noetic build does not need:

\begin{enumerate}
\item \textbf{C++ standard.} \texttt{ov\_core} and \texttt{ov\_eval} request
  C++14; on this machine, \texttt{ros/console.h} pulls in a \texttt{log4cxx}
  header that requires \texttt{std::shared\_mutex} (C++17). Raise
  \texttt{CMAKE\_CXX\_STANDARD} to \texttt{17} in both packages'
  \texttt{CMakeLists.txt}.
\item \textbf{A consistent OpenCV build throughout the workspace.} This
  machine exposes a single OpenCV development package, version 4.5.4. The
  ROS-distributed \texttt{cv\_bridge} package, however, is linked against a
  separate, older OpenCV 4.2 set of libraries that Ubuntu 22.04 also carries
  for compatibility. Building MINS's own code against 4.5.4 while linking
  the distributed \texttt{cv\_bridge} mixes two different OpenCV builds in
  one process --- this is unsafe and has been observed to crash (not on
  every code path, but reproducibly on the one that matters: converting a
  camera image and running feature tracking on it). \textbf{Fix: build
  \texttt{cv\_bridge} and \texttt{image\_geometry} from source
  (\texttt{ros-perception/vision\_opencv}, \texttt{noetic} branch) inside
  \texttt{mins\_sandbox/catkin\_ws/src/}}, so they resolve to the same 4.5.4
  as the rest of the workspace:
\begin{lstlisting}[style=shell]
cd mins_sandbox/catkin_ws/src
git clone --depth 1 -b noetic \
  https://github.com/ros-perception/vision_opencv.git
rm -rf vision_opencv/opencv_tests   # not needed
catkin build cv_bridge image_geometry
\end{lstlisting}
  One further fix is needed in this freshly-cloned \texttt{cv\_bridge}:
  its own \texttt{src/CMakeLists.txt} calls \texttt{boost::regex} without
  linking \texttt{libboost\_regex} (an upstream gap, not specific to this
  project). Add \texttt{boost\_regex} to that target's
  \texttt{target\_link\_libraries} call before building.
\item \textbf{Build the rest of the workspace on top of the fixed
  \texttt{cv\_bridge}}, sourcing its \texttt{devel/setup.bash} first so
  later packages resolve against it rather than the system one:
\begin{lstlisting}[style=shell]
source /opt/ros/noetic/setup.bash
cd mins_sandbox/catkin_ws
source devel/setup.bash
catkin build
\end{lstlisting}
\end{enumerate}

\textbf{What ``verified'' means here, precisely.} All eight packages build
without error. The specific code path this fixes --- converting a
\texttt{sensor\_msgs/Image} with \texttt{cv\_bridge} and running the same
corner-detection and optical-flow calls MINS's own tracker makes on it ---
was re-run three times against real recorded camera frames (twice directly,
once under a debugger) after the \texttt{cv\_bridge} rebuild, with no crash.
\textbf{This is not the same as a validated pose estimate.} The rectangular-motion
experiment that exercises the full estimator against a measured ground truth
has not been run yet; nothing in this section should be read as MINS's
accuracy being confirmed on this robot's real sensor data end to end.

\subsection{Setting up an SSH key}

Cloning over SSH (the first command above) needs an SSH key registered
against \emph{your own} GitHub account. This is a one-time setup per
machine, and it is what replaces the practice --- found in some older
inherited documents --- of pasting a shared personal access token directly
into a clone command. A shared token grants whoever holds it the full
access rights of the account that created it, cannot be attributed to an
individual, and stays valid in every copy of the document that carries it.

\begin{enumerate}
  \item Generate a key on the machine that will clone the repository (the
  Raspberry Pi and the lab PC each need their own):

\begin{lstlisting}[style=shell]
ssh-keygen -t ed25519 -C "your_email@example.com"
# Press Enter to accept the default path (~/.ssh/id_ed25519).
# A passphrase is optional but recommended.
\end{lstlisting}

  \item Display the \textbf{public} half of the key --- this is the only
  part that ever leaves the machine. Never share the file without the
  \texttt{.pub} extension:

\begin{lstlisting}[style=shell]
cat ~/.ssh/id_ed25519.pub
\end{lstlisting}

  \item On GitHub: \emph{profile photo $\to$ Settings $\to$ SSH and GPG keys
  $\to$ New SSH key}. Give it a title identifying the machine (e.g.\
  ``RoboMaster Pi''), paste the full line printed above, and save.

  \item Verify the key works before attempting the clone:

\begin{lstlisting}[style=shell]
ssh -T git@github.com
\end{lstlisting}

  A successful setup answers with
  \texttt{Hi <username>! You've successfully authenticated, but GitHub does
  not provide shell access.} --- that message is the expected result, not an
  error.
\end{enumerate}

If you prefer HTTPS to SSH, use the second clone command instead and
authenticate with your GitHub username and a personal access token
\emph{that you generate for your own account} --- created under
\emph{Settings $\to$ Developer settings $\to$ Personal access tokens}, scoped
to repository read access, and never shared with anyone else or written into
a document.

\section{Building on Ubuntu 22.04 (lab-PC fallback only)}
\label{sec:build2204}

\textbf{Skip this section unless you are building on a lab PC running
Ubuntu 22.04.} None of it applies to the Raspberry Pi.

ROS Noetic officially targets Ubuntu~20.04 only. On 22.04, four system-level
fixes are needed before \texttt{catkin\_make} succeeds, and a fifth at launch
time. They are recorded because this project's lab PC was upgraded to 22.04
unintentionally and the workarounds took real effort to find --- not because
this is a recommended configuration.

\subsection{Fix 1: glibc symlinks}

\texttt{librt}, \texttt{libpthread}, and \texttt{libdl} were merged into
\texttt{libc.so.6} starting with glibc~2.34 (shipped in 22.04); older
binaries and build systems still look for the separate files.

\begin{lstlisting}[style=shell]
sudo ln -sf /usr/lib/x86_64-linux-gnu/libc.so.6 /usr/lib/x86_64-linux-gnu/librt.so
sudo ln -sf /usr/lib/x86_64-linux-gnu/libc.so.6 /usr/lib/x86_64-linux-gnu/libpthread.so
sudo ln -sf /usr/lib/x86_64-linux-gnu/libc.so.6 /usr/lib/x86_64-linux-gnu/libdl.so
\end{lstlisting}

\subsection{Fix 2: libpython3.8 symlink}

Referenced by \texttt{rospack} (an official ROS Noetic package):

\begin{lstlisting}[style=shell]
sudo ln -sf /usr/lib/x86_64-linux-gnu/libpython3.8.so.1 /usr/lib/x86_64-linux-gnu/libpython3.8.so
\end{lstlisting}

\subsection{Fix 3: Boost 1.71 (real libraries, not symlinks)}

ROS Noetic's official binaries need Boost~1.71; 22.04 ships 1.74, which is
ABI-incompatible for the libraries ROS actually links (regex, filesystem).
Symlinking will not work here --- the real 1.71 \texttt{.so} files are
needed:

\begin{lstlisting}[style=shell]
# Download from http://old-releases.ubuntu.com/ubuntu/pool/{main,universe}/b/boost1.71/
# the following packages: libboost-{chrono,date-time,filesystem,program-options,
# regex,system,thread}1.71.0

dpkg-deb -x <package>.deb <extract_dir>
# copy each extracted .so.1.71.0 file into /usr/lib/x86_64-linux-gnu/
sudo ldconfig
\end{lstlisting}

\textbf{Pitfall:} if a symlink already exists at the destination path
(pointing at the 1.74 library), a plain \texttt{cp} writes \emph{through}
the symlink and corrupts the real system 1.74 file. Always remove the
symlink first:

\begin{lstlisting}[style=shell]
sudo rm -f /usr/lib/x86_64-linux-gnu/libboost_<name>.so.1.74.0   # if it is a symlink
# then copy the real 1.71 file to that path
\end{lstlisting}

If this happens anyway, recovery is a straightforward package reinstall:

\begin{lstlisting}[style=shell]
sudo apt install --reinstall libboost-{chrono,date-time,filesystem,program-options,regex,system,thread}1.74.0
\end{lstlisting}

\subsection{Fix 4: ICU 67}

A dependency of Boost~1.71's regex component; 22.04 ships 66/70, not 67.

\begin{lstlisting}[style=shell]
# Download libicu67 from old-releases.ubuntu.com
# copy libicuuc.so.67*, libicui18n.so.67*, libicudata.so.67* into /usr/lib/x86_64-linux-gnu/
sudo ldconfig
\end{lstlisting}

\subsection{Building, after the four fixes}

\begin{lstlisting}[style=shell]
cd ~/carolus_ws
rm -rf build/ devel/
catkin_make --pkg ff_msgs
catkin_make
source devel/setup.bash
\end{lstlisting}

\subsection{Fix 5: LD\_PRELOAD at launch (a runtime fix, not a build fix)}

A binary compiled on 22.04 links against \texttt{liblog4cxx.so.12} and
\texttt{libtinyxml2.so.9}; ROS Noetic's own libraries
(\texttt{librosconsole.so}, \texttt{libimage\_transport.so}) expect
\texttt{.so.10}/\texttt{.so.6}. Both versions load at runtime and the 22.04
version wins global symbol resolution, which segfaults inside
\texttt{ros::console::initialize()}. The fix, scoped to the affected node in
its launch file (already applied in the launch file below, and in
\texttt{ekf\_lite.launch}):

\begin{lstlisting}[style=code,language=XML]
<env name="LD_PRELOAD"
     value="/usr/lib/x86_64-linux-gnu/liblog4cxx.so.10:/usr/lib/x86_64-linux-gnu/libtinyxml2.so.6" />
\end{lstlisting}

Apply the same pattern to any other C++ node recompiled under 22.04 that
segfaults the same way on startup.

\subsection{If an additional ROS package needs to be built from source}

Packages unavailable via \texttt{apt} on 22.04 (e.g.\ \texttt{robot\_localization},
for planned EKF sensor-fusion work) can fail with CMake errors
about a missing \texttt{<pkg>Config.cmake} or a nonexistent
\texttt{orocos\_kdl} include path --- seven packages
(\texttt{eigen\_conversions}, \texttt{tf2\_geometry\_msgs},
\texttt{kdl\_parser}, \texttt{kdl\_conversions},
\texttt{robot\_state\_publisher}, \texttt{tf2\_kdl},
\texttt{tf\_conversions}) are broken this way by the 20.04$\to$22.04
packaging difference. Without root access to fix the real files under
\texttt{/opt/ros/noetic/}, the working solution is a set of locally
corrected copies in \texttt{carolus\_ws/cmake\_shims/<pkg>\_fix/}, given

\subsection{The pose timestamp: \texttt{stamp\_from\_acquisition}}

\texttt{/pose}'s header is stamped with the ACQUISITION time of the image it
was computed from, not the time it was published --- \textbf{leave this at
its default of \texttt{true}.} The alternative
(\texttt{stamp\_from\_acquisition:=false}) reproduces the old behaviour,
where every pose is stamped \texttt{ros::Time::now()} at the moment Carolus
finishes computing it. That difference is not cosmetic: a fusion filter
reads \texttt{header.stamp} to place the measurement in time, so the old
behaviour hands it a systematic offset it has no way to detect, and it also
makes the pose's real latency unmeasurable from ROS alone --- the gap
between capture and publication silently disappears into "now".

\begin{lstlisting}[style=shell]
roslaunch carolus_node testcarolus.launch stamp_from_acquisition:=false
\end{lstlisting}

The only legitimate reason to set it \texttt{false} is if the image
timestamps come from a machine whose clock is not synchronised with
whatever consumes \texttt{/pose} --- and even then, fix the clock sync
rather than the stamp. \textbf{Check this before trusting it}: the Pi's
system clock is not guaranteed to be NTP-synchronised (observed drifted by
several days on this project, 2026-08-10), and a drifted clock corrupts
this exact mechanism silently, the same way the old publish-time stamping
did.

\section{Verifying it is running}

\begin{lstlisting}[style=shell]
rosnode info /carolus_astrobee_rex
rostopic hz /pose
rostopic hz /postprocessed/image
\end{lstlisting}

With a beacon visible to the camera, \texttt{/pose} publishes a
\texttt{geometry\_msgs/PoseStamped}. Visualize blob detection in RViz by
adding an \textbf{Image} display on \texttt{/postprocessed/image}: correctly
detected blobs appear as small circles over the live feed.

\textbf{Check the latency, not just the rate.} A high \texttt{/pose} rate
says nothing about whether \texttt{stamp\_from\_acquisition} landed
correctly (previous section). In the camera bridge's own log
(\texttt{rm\_cam\_beacon.py}, Chapter~\ref{ch:camera}), every 50 poses
prints \texttt{[LATENCY] /pose NN ms (mean over 50 poses)} --- a plausible
value confirms acquisition-time stamping and synchronised clocks. A value
outside $-1$--5000\,ms instead logs
\texttt{[LATENCY] implausible (NN ms) --- /pose is probably stamped at
publication time, not acquisition}, naming the same two causes: an old
binary running without the flag, or the two machines' clocks disagreeing.

\begin{warningbox}
\textbf{Checkpoint --- the core pipeline is now complete.} With a powered
beacon in the camera's view, \texttt{rostopic hz /pose} reports roughly
13\,Hz on the Pi. No beacon in view means no pose at all --- that is correct
behaviour, not a fault. Once this passes, go to Chapter~\ref{ch:launcher} to
actually drive the robot.
\end{warningbox}

\section{Beacon geometry and blob-filtering parameters}
\label{sec:beacon-params}

The parameters most likely to need tuning for a new beacon or lighting
condition:

\begin{center}
\begin{tabular}{ll}
\toprule
Parameter & Meaning \\
\midrule
\texttt{min\_circularity} & Rejects non-round contours; closer to 1 is stricter. \\
\texttt{saturation\_threshold} & Rejects low-saturation pixels (in HSV) before hue filtering. \\
\texttt{min\_area}, \texttt{max\_area} & Rejects contours outside this pixel-area range. \\
\texttt{max\_distance\_lim} & Rejects candidate 4-blob groups whose pairwise distances exceed this. \\
\texttt{lb\_hue}, \texttt{ub\_hue} & Hue range the beacon's LEDs must fall within, in \textbf{OpenCV's 0--180 scale}, not 0--360. \\
\bottomrule
\end{tabular}
\end{center}

\textbf{The hue scale is worth stating explicitly, because getting it wrong
silently kills all detection.} OpenCV stores hue on 0--180 (half the usual
0--360 degree circle, so it fits in one byte), and the node compares the
blob's mean hue against \texttt{lb\_hue}/\texttt{ub\_hue} on that same
0--180 scale. Rough reference points: red $\approx$ 0--10 and 170--180,
green $\approx$ 50--80, blue $\approx$ 100--140. This project's beacon uses
blue LEDs, hence the 90--140 window in the launch file. If you enter a value
from the 0--360 convention (e.g.\ 240 for blue), every blob is rejected and
the node runs normally while never publishing a pose.

\begin{warningbox}
\textbf{This beacon has a physical LED intensity control.} Turning it
changes every LED's brightness at once, which shifts the blob's measured
saturation and can push it outside \texttt{saturation\_threshold},
\texttt{min\_area}/\texttt{max\_area}, or the hue window above --- \textbf{the
whole table on this page is only valid for the intensity the beacon was set
to when these values were tuned.} If the knob has been touched since, or you
are not sure, re-run the detection tuning (adjust the parameters above while
watching \texttt{[BEACON] status=DETECTED} in the launcher log) before
trusting any pose Carolus reports. This does not affect \texttt{known\_points}
below, which is a geometric measurement, not a brightness one --- but a
beacon that has been physically disassembled or rebuilt needs that
re-measured too.
\end{warningbox}

\texttt{known\_points} is the beacon's four LED positions in metres, in
Carolus's own left-handed frame, with one point deliberately off the plane
of the other three (needed for P4P to resolve pose unambiguously).
\textbf{These are a physical measurement of this project's specific beacon,
not a universal constant} --- the same caveat as the camera intrinsics in
Chapter~\ref{ch:calibration}. A beacon built to different dimensions needs
these four points re-measured and substituted; reusing this project's values
against a differently-sized beacon will make the P4P solve fail silently or
produce a plausible-looking but wrong pose.

\begin{warningbox}
\textbf{The \emph{sign} of the out-of-plane coordinate matters more than its
magnitude, and getting it wrong is nearly undetectable.} Recording the fourth
LED on the wrong side of the plane of the other three --- writing
\texttt{+0.0555} where the hardware has it at \texttt{-0.0555} --- describes
a beacon that is the mirror image of the real one. The solver still
converges, the residual still looks healthy, and the reported pose is still
a valid rotation. What changes is its handedness: rotations about two of the
three axes come back with \textbf{inverted sign}, while the third reads
correctly.

Demonstrated numerically rather than assumed (2026-08-11): projecting the
real four-LED geometry and re-solving with that one coordinate's sign
flipped inverts the recovered rotation about X and Y while leaving Z
correct. By contrast, corrupting the \emph{camera intrinsics} severely --- a
25\% focal-length error, a 60-pixel principal-point shift, and distortion
ignored entirely --- shifts the recovered angles by only a few percent and
\textbf{never flips a sign}.

Practical consequence: if orientation readings look mirrored, suspect this
value's sign before suspecting the camera calibration. Measure which side of
the plane the fourth LED sits on and confirm it against the sign written
here.
\end{warningbox}

\chapter{Converting a Carolus Pose into the ROS Frame}
\label{ch:tf-conversion}

\runson{the machine running the TF broadcaster --- normally the \textbf{Raspberry Pi}, alongside Carolus itself.}

Carolus reports where the beacon is \emph{in its own camera frame}. Every ROS
consumer downstream --- TF2, RViz, any sensor-fusion filter --- expects
REP-103 conventions instead. This chapter derives that conversion rather than
just stating the constant, because the constant alone is impossible to check
and easy to get subtly, silently wrong.

\section{Why this is harder than it looks}

Two independent earlier integrations of Carolus, on a Leo Rover and on a
Limo, each arrived at their conversion constants by trial and error against
real hardware. Both worked on their own platform. Neither derivation was
written down, so neither transfers, and there is no way to tell from the
constants alone whether they encode a genuine convention difference or a
compensating error.

The failure mode this invites is specific and nasty: an orientation
conversion that is wrong can still produce a perfectly valid unit quaternion.
Nothing raises an error, RViz draws a plausible set of axes, and the mistake
only surfaces as motion in the wrong direction much further downstream.

\section{Step 1 --- what Carolus actually publishes}

Carolus's P4P solver minimises reprojection error in the standard
computer-vision form: for each known beacon LED at position $\mathbf{p}_b$ in
the \emph{beacon's} own frame, it predicts a pixel by

\[
\mathbf{p}_c \;=\; R_{\text{solved}}\,\mathbf{p}_b \;+\; \mathbf{t},
\qquad
u = f_x\frac{p_{c,x}}{p_{c,z}} + c_x,
\qquad
v = f_y\frac{p_{c,y}}{p_{c,z}} + c_y .
\]

$R_{\text{solved}}$ therefore maps \emph{beacon-frame} coordinates into
\emph{camera-frame} coordinates: it is $R_{\text{beacon}\to\text{camera}}$.
This is the same convention OpenCV's \texttt{solvePnP} documents for its own
output, and the two are interchangeable as a sanity check.

\textbf{But that is not what reaches the ROS topic.} Before publishing,
Carolus transposes it. What appears in the \texttt{/pose} message's
\texttt{orientation} field is

\[
R_{\text{published}} \;=\; R_{\text{solved}}^{\top} \;=\; R_{\text{camera}\to\text{beacon}} .
\]

\begin{warningbox}
This transpose is the single most commonly missed step. A quaternion built
from $R_{\text{published}}$ describes the \emph{opposite} rotation to the one
the solver computed. Both are valid quaternions; only one is the one you
want.
\end{warningbox}

\section{Step 2 --- what TF2 expects}

The broadcaster publishes the edge
\texttt{camera\_link}~$\rightarrow$~\texttt{beacon\_observed}. By TF2's
convention, the rotation on a parent~$\rightarrow$~child edge must take a
vector expressed in the \emph{child} frame and give it in the \emph{parent}
frame. Here that is beacon~$\rightarrow$~camera:

\[
R_{\text{needed}} \;=\; R_{\text{beacon}\to\text{camera}}
\;=\; R_{\text{published}}^{-1}.
\]

So the published quaternion must be \textbf{inverted} before anything else is
done to it. Combined with Step~1, the two transposes do not cancel: the
solver transposes once on the way out, and the TF convention requires
inverting once on the way in.

\section{Step 3 --- the change of basis, and why it is proper}

The remaining task is to re-express that rotation from Carolus's camera axes
($X$ right, $Y$ down, $Z$ forward) in ROS's body axes ($X$ forward, $Y$ left,
$Z$ up). Writing the correspondence as a matrix acting on coordinate columns:

\[
B \;=\;
\begin{bmatrix}
0 & 0 & -1\\
1 & 0 & 0\\
0 & -1 & 0
\end{bmatrix},
\qquad \det B = +1 .
\]

Both frames are right-handed, so $B$ is necessarily a proper rotation. An
improper (determinant~$-1$) matrix here would assert that one of the two
frames is a mirror image of what its own convention says, which is not the
case for either.

\section{Step 4 --- a rotation is re-based by conjugation, not permutation}

This is the step both prior integrations had to find empirically. A
\emph{vector} changes basis by a single multiplication, $\mathbf{v}' =
B\mathbf{v}$. A \emph{rotation operator} does not: it must be conjugated,

\[
R' \;=\; B\,R\,B^{-1},
\qquad\text{equivalently}\qquad
q' \;=\; b \otimes q \otimes b^{-1},
\]

where $b$ is the unit quaternion corresponding to $B$. Permuting and
negating the components of $q$ directly --- the tempting shortcut, because it
is what works for a vector --- is not the same operation and does not
generally give the same result.

\begin{warningbox}
The quaternion form $q' = b \otimes q \otimes b^{-1}$ exists only when $B$ is
proper. Unit quaternions parametrise proper rotations and nothing else, so an
improper change of basis has no quaternion representation at all and must be
handled as a matrix. This is another reason to establish the determinant
before reaching for quaternions.
\end{warningbox}

\section{The result}

Composing Steps 1--4, with $q$ the quaternion read from \texttt{/pose}:

\[
\boxed{\;q_{\text{ROS}} \;=\; b \otimes q^{-1} \otimes b^{-1}\;}
\]

and the position, which is an ordinary vector and so takes the single
multiplication:

\[
(x,y,z)_{\text{ROS}} \;=\; (-z,\; x,\; -y)_{\text{camera}} .
\]

In the broadcaster this is a few lines: build $b$ once from $B$ at import
time, invert the incoming quaternion, conjugate, normalise, publish.

\section{Cross-checking the result against an independent implementation}

A derivation that only reproduces its own assumptions is worth little. The
Limo integration mentioned earlier arrived, by trial and error and with no
derivation, at a component-wise rule for its own quaternion conversion, using
the same axis correspondence $B$ as above.

Evaluating both expressions on randomly generated unit quaternions gives
identical rotations, agreeing to machine precision (differences of order
$10^{-16}$, i.e.\ floating-point round-off) across every trial. The formula
derived here therefore \emph{predicts} an empirical result obtained
independently, on different hardware, by people who were not deriving it ---
which is the strongest available evidence that the derivation is not merely
self-consistent.

Applying the same comparison to the pre-correction formula (composition
without the inversion of Step~2) gives a substantially different rotation on
every trial, confirming the inversion is load-bearing rather than cosmetic.

\section{Validation status}

\textbf{Verified:} the derivation above, checked against the solver's own
source; the determinant argument, checked against REP-103's stated axis
conventions; and the numerical agreement with the independent Limo result,
computed directly.

\textbf{Not yet verified:} an end-to-end physical measurement on this robot
--- placing the beacon at a known orientation and comparing
\texttt{rosrun tf tf\_echo camera\_link beacon\_observed} against it. Until
that is done, treat this chapter as a derivation that has passed every
available desk check but has not been confirmed against a ruler. The test
itself is cheap: rotate the beacon by a known angle about one camera axis at
a time and confirm the reported rotation matches in both axis and sign. Note
that a $180^\circ$ test rotation cannot distinguish a correct conversion from
a mirrored one --- the two coincide exactly at that angle --- so use
something well away from both $0^\circ$ and $180^\circ$.

Use the launcher's \texttt{Kill}, or close the window --- both clean up the

\begin{warningbox}
\textbf{An orphaned \texttt{rm\_cam\_beacon.py} breaks the next session.}
It keeps the robot's single SDK connection open, so the next launch hits
the double-connection failure --- motion commands stop responding with no
error anywhere. If you ever kill processes by hand, \textbf{bracket the
pattern}: \texttt{pkill -f "[r]m\_cam\_beacon"}. Without the bracket, the
remote shell's own command line contains the pattern and \texttt{pkill}
can kill that shell before it reaches the real target, non-deterministically
and with nothing reported.
\end{warningbox}

\section{Beacon docking (T5)}
\label{sec:docking}

\textbf{Status: works, with a known limitation --- read this before running
it near anything fragile.} The docking behaviour drives the robot to a fixed
distance from the beacon (0.20\,m) in three phases: align the gimbal to the
beacon, rotate the chassis until it agrees with the gimbal, then drive
forward.

The \textbf{DOCKING BALISE} panel has four buttons:

\begin{center}
\begin{tabular}{p{0.22\textwidth}p{0.70\textwidth}}
\toprule
Button & What it does \\
\midrule
\texttt{CALIBRATE} & Step 1 of a two-step calibration: measures the beacon
  face-on. \\
\texttt{CAL STEP 2} & Step 2: measures again after \emph{you} have pivoted
  the robot roughly 30--45\,\textdegree{}. No time pressure between the two
  steps. \\
\texttt{START} & Runs the docking sequence. \\
\texttt{ABORT} & Stops it. \\
\bottomrule
\end{tabular}
\end{center}

The buttons only unlock once the node has reported its own status at least
once --- commands sent before that used to be silently dropped.

\begin{warningbox}
\textbf{Known limitation, unresolved:} nothing corrects the chassis heading
\emph{during} the drive --- only the camera tracks the beacon. A run can
therefore finish close to the beacon but off-centre. A collision has
happened once on this project, caused by a silent gimbal-probe failure that
let the chassis align to the wrong reference (since fixed, with a retry and
an abort guard). \textbf{Run docking with clear space around the robot, and
keep a hand near ABORT.}
\end{warningbox}

\chapter{Troubleshooting}
\label{ch:troubleshooting}

\runson{wherever the symptom appears. Each entry names the machine to check
on.}

Work down from the symptom. Each step either fixes the problem or rules out
a layer --- the ordering matters, because a dead network link and a dead
node look identical from most checks.

\section{Nothing responds: the robot ignores every command}

\begin{enumerate}
  \item \textbf{Did the robot chime twice at power-on?} One chime means the
  root hack is not active and the SDK will not answer at all
  (Chapter~\ref{ch:poweron}). Power-cycle and listen again.
  \item \textbf{Is a second script holding the SDK?} Only
  \texttt{rm\_cam\_beacon.py} may connect. On the Pi:
  \texttt{pgrep -af "[r]m\_cam\_beacon"} --- more than one result, or an
  orphan from a previous session, causes exactly this symptom with no error
  message anywhere. Kill it and relaunch.
  \item \textbf{Is the RNDIS link up?} From the Pi:
  \texttt{ping -c4 192.168.42.2}. It does not survive a Pi reboot
  (Chapter~\ref{ch:network}).
\end{enumerate}

\section{The Pi will not turn on}

The cable is almost certainly in the Pi's own POWER IN port instead of the
UPS HAT's port underneath. Check that the HAT's blue charge LED is lit
(Section~\ref{sec:pi-power}).

\section{\texttt{rostopic} from the lab PC finds nothing}

\begin{enumerate}
  \item \textbf{Is the node actually running?} On the Pi:
  \texttt{pgrep -af "[r]m\_cam\_beacon"}.
  \item \textbf{If it is running but invisible from the PC}, the shell that
  launched it was missing \texttt{ROS\_MASTER\_URI}/\texttt{ROS\_IP} ---
  \texttt{rospy} falls back to \texttt{localhost} and the node is reachable
  only from the Pi itself. Relaunch with both exported
  (Chapter~\ref{ch:camera}). This is the single most common cause.
  \item \textbf{Is your own shell pointed at the right master?} On the PC:
  \texttt{echo \$ROS\_MASTER\_URI} should read
  \texttt{http://192.168.0.103:11311}.
  \item \textbf{A black image or an \texttt{AF\_INET} error} instead of no
  topic at all is hostname resolution --- add the Pi to
  \texttt{/etc/hosts} on the PC (Chapter~\ref{ch:network}).
\end{enumerate}

\section{The camera publishes but \texttt{/pose} never does}

\begin{enumerate}
  \item \textbf{Is a beacon actually in view, powered on?} Check
  \texttt{[BEACON] status=} in the T2 log, or the launcher's beacon
  indicator. \texttt{[DUTY] beacon in view 0.0\%} confirms it is not.
  \item \textbf{Is Carolus running?} On the Pi:
  \texttt{pgrep -f carolus\_astrobee}.
  \item \textbf{Are the hue bounds right for your LEDs?} This is the classic
  silent failure: the node runs, looks healthy, and rejects every blob.
  \texttt{lb\_hue}/\texttt{ub\_hue} are on \textbf{OpenCV's 0--180 scale},
  not 0--360 --- entering 240 for blue rejects everything. See the end of
  Chapter~\ref{ch:carolus-node}.
  \item \textbf{Are all four LEDs visible?} P4P needs four points; three is
  not enough and produces nothing rather than a degraded pose.
\end{enumerate}

\section{The keyboard does not drive the robot}

\begin{enumerate}
  \item \textbf{Is the launcher in MANUAL mode?} The button must read
  \texttt{MODE: MANUAL} in orange (Chapter~\ref{ch:launcher}).
  \item \textbf{Move the mouse over the launcher window} --- an external
  terminal opened by T1/T3 has probably stolen keyboard focus.
  \item \textbf{Numpad specifically dead?} LOCK is on and holds the gimbal
  exclusively. The chassis keys should still work.
\end{enumerate}

\section{\texttt{/imu} is silent}

Do not suspect the robot first. If a ROS publisher is created \emph{after}
its SDK subscription, the first callback raises inside the SDK's dispatcher
thread and kills it --- after which no telemetry callback ever fires again,
with the topic still advertised and nothing logged. See the second warning
box in Chapter~\ref{ch:camera}.

\section{The build fails}

On the Pi (Ubuntu 20.04) the build is standard; a failure there is usually
memory --- pass \texttt{-j2}. On a lab PC running Ubuntu 22.04, the five
fixes in Section~\ref{sec:build2204} are all required, and a segfault at
launch rather than at build time is Fix 5 (the \texttt{LD\_PRELOAD}).

\section{Messages you can safely ignore}

Three appear routinely on a healthy system and have each cost someone an
afternoon:

\begin{itemize}
  \item \texttt{bash: .../catkin\_ws/devel/setup.bash: No such file or
  directory} --- a leftover line in a shell profile. Harmless.
  \item \texttt{WARNING: disk usage in log directory [...] is over 1GB} ---
  accumulated ROS logs. \texttt{rosclean purge} when convenient.
  \item \texttt{imageio 2.35.1 has requirement pillow>=8.3.2, but you'll
  have pillow 7.0.0} --- from \texttt{myqr}, a transitive dependency of the
  SDK used only for Wi-Fi QR codes, which this RNDIS setup never uses.
\end{itemize}
