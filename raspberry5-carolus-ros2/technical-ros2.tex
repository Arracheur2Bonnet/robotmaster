\begin{abstract}
This document is deliberately \textbf{self-contained and independent of the
main Carolus/RoboMaster manual} (\texttt{overleaf/technical.tex}) and of the
rest of that project's repository. It, and the folder it lives in
(\texttt{raspberry5-carolus-ros2/}), can be copied, moved, or handed over on
their own and still work: the ROS2 wrapper source
(\texttt{carolus\_ros2/}) holds its own copy of the detection/solver core
rather than referencing another workspace by relative path, and every
install step below is written out in full rather than pointed at another
document. \textbf{The cost of that choice, stated plainly:} the C++ core
copied into \texttt{carolus\_ros2/src/} and \texttt{include/carolus\_node/}
is a snapshot, not a live link --- if the ROS1 node's own copy
(\texttt{carolus\_ws/src/libuvgs\_astrobee/}) is fixed or changed later, this
copy does not update itself, and someone has to notice and re-sync it by
hand. Accepted on purpose, because this document's job is to be portable,
not to be the single source of truth for that source code.

\textbf{What Carolus is, for a reader with no other context:} a physical
4-LED target (the \emph{beacon}) is detected in a camera frame, and a
Perspective-4-Point (P4P) solve on the four blob centres yields a full
6-DOF camera pose relative to it --- originally derived from NASA's SVGS
system for the Astrobee free-flyer, adapted here for a DJI RoboMaster S1.
The ROS1 node running this today is \texttt{carolus\_astrobee}.

This is the ROS2 side of Carolus, in full: what it took to build and run the
same detection/pose pipeline under ROS2, on two different machines. No
robot is involved anywhere in this document --- both targets run against a
plain USB webcam, or a synthetic image.
\end{abstract}

\section{Why this exists}

The Carolus/RoboMaster project's ROS1 node (\texttt{carolus\_astrobee}) mixed
its detection algorithm (blob preprocessing, contour extraction, blob
selection) with its ROS wiring inside one class. The detection methods'
\emph{signatures} were already framework-agnostic ---
\texttt{cv::Mat}/\texttt{std::vector}/\texttt{double}, no ROS types --- but
their \emph{bodies} called ROS logging macros directly, which is real
coupling a signature alone does not show.

That algorithm was extracted into a separate library, \texttt{carolus\_core}
(\texttt{beacon\_detector.cpp} plus \texttt{ceresP4P.cpp}/\texttt{pose\_est.cpp}/%
\texttt{pose\_filter.cpp}), built with zero ROS headers and zero ROS linkage
--- confirmed by an empty \texttt{NEEDED} list on the compiled library, not
assumed from reading the source. The ROS1 node links against it instead of
containing it; this chapter (and the next) builds the exact same source a
second and third time, under different toolchains and middlewares, as the
actual test of that claim --- not that the code compiles, but that it
produces the same numbers.

\section{Where this node genuinely differs from the ROS1 one}
\label{sec:ros2-vs-ros1}

The detection and solver core is the same source. The \emph{wrappers} around
it are not, and the differences below change the published numbers --- so a
ROS1-vs-ROS2 comparison run with both nodes' defaults is not comparing like
with like. Verified against both sources 2026-09-03.

\begin{center}
\begin{tabular}{@{}p{0.20\textwidth}p{0.37\textwidth}p{0.35\textwidth}@{}}
\toprule
& ROS1 (\texttt{carolus\_astrobee}) & ROS2 (\texttt{carolus\_ros2}) \\
\midrule
Distortion model & \texttt{fov}, \texttt{fisheye} or plumb\_bob, selected per profile. The Logitech profile sets \texttt{fov: false} (BUG-138, fixed 2026-09-04) & plumb\_bob always; no \texttt{fov} branch exists \\
Pose filtering & \texttt{PoseFilter} active: FIFO of 7, translation gate 0.5\,m, rotation gate 0.3 & \textbf{not called} --- publishes the raw per-frame solve \\
Image subscription & \texttt{image\_transport} & plain \texttt{rclcpp} subscription \\
Default image topic & \texttt{/usb\_cam/image\_raw} & \texttt{/image\_raw} \\
\texttt{known\_points} format & space-separated string & real YAML list \\
Astrobee landmarks & publishes \texttt{ff\_msgs/VisualLandmarks} & not published \\
Camera pixel format & \texttt{yuyv} (its launch file) & \texttt{mjpeg2rgb} \\
\bottomrule
\end{tabular}
\end{center}

Identical on both, and not a source of divergence: the intrinsics and every
detection parameter (both profiles carry the same measured values), the
warm-start, and the 24-candidate correspondence search --- default
\texttt{true} on both since 2026-09-03. Colour handling also agrees despite
the different pixel formats: ROS1 converts \texttt{rgb8} to BGR explicitly
before \texttt{COLOR\_BGR2HSV}, ROS2 asks \texttt{cv\_bridge} for
\texttt{bgr8} outright.

\begin{warningbox}
\textbf{One more setting to change before any parity measurement} ---
\texttt{fifo\_on} is a real feature, not a bug, so it is not changed in the
checked-in profile permanently. \texttt{carolus.launch} loads the profile
via \texttt{rosparam command="load"}, with no launch argument exposed for
this key, so the verified way to override it for one comparison run is to
edit \texttt{fifo\_on: true} to \texttt{false} directly in
\texttt{logitech\_1080p.yaml} before launching, and change it back
afterward --- the same edit-run-revert pattern this project already uses for
exposure. ROS1 publishes a 7-pose sliding average with outlier rejection;
ROS2 publishes each raw solve. Comparing a filtered output against an
unfiltered one measures the filter as much as the solver.

\texttt{false} is correct only for this comparison, never as a standing
setting. Left off permanently, ROS1 loses the one thing this filter
provides that ROS2's own wrapper does not: rejection of a single bad frame
before it ever reaches \texttt{/pose}, protection this project has
directly needed in practice, not only in principle.
\end{warningbox}

\subsection{Where the comparison itself lives}
\label{sec:ros2-vs-ros1-no-third-tree}

\textbf{Decided 2026-09-04: exactly two trees are maintained, and no third
one is added for this comparison.} \texttt{carolus\_ws/} (ROS1) and this
folder (ROS2) already duplicate the detection/solver core once, a
deliberate, accepted cost this document's opening section states plainly ---
\texttt{shortcuts/ros2\_sync\_check.sh} exists because that duplication needs
watching. A third copy (a \texttt{test\_ros/} holding its own patched builds
of both stacks plus calibration data, considered explicitly this session)
would need its own drift check on top of that one, for a comparison that is
methodology and results, not code. It was rejected on that basis, not on
time or effort grounds.

Concretely, each piece of the comparison has exactly one home, none of them
a new folder:

\begin{center}
\begin{tabular}{@{}p{0.30\textwidth}p{0.62\textwidth}@{}}
\toprule
What & Where \\
\midrule
The two trees' known differences (this section) and the settings to align before comparing & here, \texttt{technical-ros2.tex} \\
What the comparison found, and what it means & \texttt{overleaf/main.tex} --- a finding, not a procedure \\
Whether the two trees' shared core has drifted & \texttt{shortcuts/ros2\_sync\_check.sh}, already run after every change to either copy \\
Calibration images for whichever camera is under test & \texttt{data/checkerboard/<camera>\_<date>/}, the convention already in use --- one dated folder per calibration session, not per comparison \\
\bottomrule
\end{tabular}
\end{center}

\textbf{Measured 2026-09-04:} with the settings above aligned, ROS1 and
ROS2 agree to 1.1\,mm ($0.7017$\,m vs $0.7028$\,m, both against a
$\sim$70\,cm tape measurement) --- the same beacon and camera, moved from
one machine to the other between runs. Full account and the investigation
that preceded it: \texttt{overleaf/main.tex}.

\begin{warningbox}
\textbf{BUG-138, fixed 2026-09-04, for the record: what the Logitech profile
got wrong and why.} It shipped \texttt{fov: true}, which routes undistortion
through the Astrobee single-parameter FOV model. That model reads
\texttt{distortion[0]} --- the profile's plumb\_bob \textbf{k1} --- as its
own, unrelated field-of-view coefficient, computing
$r_u = \tan(r_d k_1) / 2\tan(k_1/2)$. For a $k_1$ this small that is
algebraically the identity: against the four measured blob positions at
83\,cm it gave 0.99979--0.99980 where plumb\_bob gives 1.00010--1.00088.
\textbf{The measured distortion was silently discarded, and k2 was never
read at all.} The error was well under a millimetre at this range with this
lens. \texttt{fov: false} now routes the same profile through
\texttt{cv::undistortPoints}, which is what its distortion array was
actually calibrated for.

\textbf{This was not a Logitech-only mistake.} The same \texttt{fov: true}
plus a full plumb\_bob distortion array appears in \texttt{robomaster\_s1.yaml}
and \texttt{robomaster\_s1\_longrange.yaml} --- the S1's own operational
profiles. Computed against those coefficients ($k_1=-0.1479$,
$k_2=0.1452$), the same mismatch reaches \textbf{$-2.8\,\%$ at 250\,px off
the optical centre} (an approximate $f_x=500$ stand-in was used for this
estimate, not this camera's own calibrated value), an order of magnitude
larger than the Logitech case. \textbf{Deliberately not fixed here} ---
changing the robot's own camera model is a live-parameter change to
hardware currently in service, and this project's own comment in that file
already flags the distortion array as ``validated pragmatically rather than
by a formal calibration campaign,'' so switching to \texttt{cv::undistortPoints}
is not guaranteed correct without first checking that array actually fits a
plumb\_bob model. Tracked as BUG-139.
\end{warningbox}

\section{Getting Carolus's own source code onto a blank machine}
\label{sec:ros2-onto-blank-machine}

\textbf{This one \texttt{git clone} is the only step that gets Carolus's
actual ROS2 source code (\texttt{carolus\_ros2/}) onto your machine ---
there is no separate ``download Carolus'' step anywhere else in this
document, and no second repository.} Every later command in this chapter
(building, testing, calibrating) assumes this clone already happened.
On a genuinely blank machine it has not, and \texttt{git} itself is not
installed by default on a minimal Ubuntu image either:

\begin{lstlisting}[style=shell]
sudo apt install -y git
git clone -b nawfel-legacy https://github.com/Arracheur2Bonnet/robotmaster.git
\end{lstlisting}

\texttt{raspberry5-carolus-ros2/}, the name this whole document uses for
itself, is \texttt{robotmaster/\allowbreak raspberry5-carolus-ros2/} inside
that clone --- and \texttt{carolus\_ros2/} inside \emph{that} is the actual
buildable ROS2 package (Section~\ref{sec:ros2-carolus-package}), not a
placeholder for something fetched separately later.

\textbf{This is deliberate, not incidental: \texttt{raspberry5-carolus-ros2/}
is a self-contained folder, independent of the rest of the
\texttt{robotmaster} repository.} It carries its own copy of the
detection/solver core rather than a relative reference into
\texttt{carolus\_ws/src/}, precisely so it can be cloned, copied, or handed
to someone else and built entirely on its own. Nothing outside this one
folder --- not \texttt{carolus\_ws/}, not any other part of the clone --- is
needed to build or run Carolus under ROS2.
\textbf{Found missing 2026-08-24}, following this document literally on a
second, genuinely blank 24.04 machine: nothing above this point mentioned
either step, despite every later command assuming both were already done.

\section{Installing ROS2 Humble}

Ubuntu 22.04 is Humble's own native target, so it installs from the official
packages:

\begin{lstlisting}[style=shell]
sudo apt update
sudo apt install software-properties-common curl -y
sudo add-apt-repository universe -y
sudo curl -sSL https://raw.githubusercontent.com/ros/rosdistro/master/ros.key \
    -o /usr/share/keyrings/ros-archive-keyring.gpg
echo "deb [arch=$(dpkg --print-architecture) \
    signed-by=/usr/share/keyrings/ros-archive-keyring.gpg] \
    http://packages.ros.org/ros2/ubuntu $(. /etc/os-release && echo $UBUNTU_CODENAME) main" \
    | sudo tee /etc/apt/sources.list.d/ros2.list > /dev/null
sudo apt update
sudo apt install ros-humble-ros-base ros-humble-cv-bridge \
    python3-colcon-common-extensions \
    libeigen3-dev libceres-dev libopencv-dev build-essential cmake -y
\end{lstlisting}

\begin{warningbox}
\texttt{ros-humble-ros-base} alone does \textbf{not} include
\texttt{cv\_bridge} --- the same gap exists on the ROS1 side of this project
(\texttt{ros-noetic-ros-base} vs. \texttt{ros-noetic-desktop-full}), and
skipping it here reproduces the same broken-build failure on ROS2.
\texttt{image\_transport} is deliberately \textbf{not} in this list ---
\texttt{carolus\_ros2}'s \texttt{package.xml} and \texttt{CMakeLists.txt}
declare no dependency on it (checked directly, not inferred), a direct
consequence of BUG-127 (Chapter~\ref{ch:ros2-pi5}) replacing
\texttt{image\_transport::create\_subscription} with a plain
\texttt{rclcpp::create\_subscription}. An earlier revision of this
install command listed it anyway, left over from before that fix; installing
it does no harm, but nothing here needs it. The four packages after
\texttt{python3-colcon-common-extensions} are not ROS packages at all ---
they are \texttt{carolus\_core\_ros2}'s own C++ dependencies
(\texttt{find\_package(Eigen3/Ceres/OpenCV)} in its \texttt{CMakeLists.txt}),
easy to miss because this project's own lab PC already had them installed
from unrelated ROS1 work, which is exactly the trap: a dependency that is
satisfied by accident on the machine that wrote this document is invisible
until a genuinely blank machine tries to build it.
\end{warningbox}

\section{Installing ROS2 Jazzy, in a container}
\label{sec:ros2-jazzy-container}

Jazzy targets Ubuntu 24.04, not 22.04 --- installing its packages natively on
a 22.04 host risks library-version ABI mismatches between what Jazzy expects
and what the host actually has. A container sidesteps the question rather
than risking it:

\begin{lstlisting}[style=shell]
docker pull ros:jazzy-ros-base
docker run -d --name carolus_jazzy \
    -v /path/to/raspberry5-carolus-ros2:/carolus_ros2_ws \
    ros:jazzy-ros-base sleep infinity
docker exec carolus_jazzy apt-get update
docker exec carolus_jazzy apt-get install -y \
    ros-jazzy-cv-bridge \
    python3-colcon-common-extensions \
    libeigen3-dev libceres-dev libopencv-dev build-essential cmake
\end{lstlisting}

\texttt{/path/to/raspberry5-carolus-ros2} is a placeholder, here and
everywhere else it appears in this document --- substitute this folder's
actual absolute path on your machine.

\section{Installing ROS2 Jazzy, natively (no container) --- on an actual 24.04 machine}
\label{sec:ros2-jazzy-native-pc}

The container above exists for one reason only: this document was written
on a 22.04 machine, and Jazzy targets 24.04. \textbf{If your machine
genuinely runs Ubuntu 24.04, skip the container entirely} --- the
mismatch Section~\ref{sec:ros2-jazzy-container} exists to sidestep is gone,
and native install is simpler:

\begin{lstlisting}[style=shell]
sudo apt update
sudo apt install software-properties-common curl -y
sudo add-apt-repository universe -y
sudo curl -sSL https://raw.githubusercontent.com/ros/rosdistro/master/ros.key \
    -o /usr/share/keyrings/ros-archive-keyring.gpg
echo "deb [arch=$(dpkg --print-architecture) \
    signed-by=/usr/share/keyrings/ros-archive-keyring.gpg] \
    http://packages.ros.org/ros2/ubuntu $(. /etc/os-release && echo $UBUNTU_CODENAME) main" \
    | sudo tee /etc/apt/sources.list.d/ros2.list > /dev/null
sudo apt update
sudo apt install ros-jazzy-ros-base ros-jazzy-cv-bridge \
    python3-colcon-common-extensions \
    libeigen3-dev libceres-dev libopencv-dev build-essential cmake -y
\end{lstlisting}

Identical in shape to Section~\ref{sec:ros2-jazzy-container}'s container
install and to the Pi 5's own native install
(Chapter~\ref{ch:ros2-pi5}) --- same packages, same reasoning for each
one (\texttt{ros-jazzy-ros-base} alone omits \texttt{cv\_bridge};
\texttt{image\_transport} is deliberately absent, unneeded since BUG-127).
The only thing that changes between all three paths is whether a container
sits underneath.

\begin{warningbox}
\textbf{Verified on genuine bare metal 2026-08-24} --- a second, dedicated
24.04 machine (\texttt{systemd-detect-virt} confirms \texttt{none}), this
section's own commands followed literally, no container, no VM. Confirms
Hector's Q1/Q2 directly: this install path works, unmodified, on real
24.04 hardware. See Section~\ref{sec:ros2-maxrate} row 5 for the throughput
result and why it is \emph{not} a clean architecture comparison against the
other rows despite being the cleanest \emph{install-path} confirmation yet.
\end{warningbox}

\section{The \texttt{carolus\_ros2} package}
\label{sec:ros2-carolus-package}

\texttt{carolus\_ros2/} is a minimal \texttt{rclcpp} wrapper --- \textbf{a
proof that the core ports, not a full reimplementation of the ROS1 node.}
Unlike an earlier version of this package, it does \textbf{not} reference
another workspace by relative path: \texttt{src/} and
\texttt{include/carolus\_node/} hold their own copy of
\texttt{beacon\_detector}/\texttt{ceresP4P}/\texttt{pose\_est}/\texttt{pose\_filter},
so this whole folder builds on its own.

Deliberately out of scope, stated here so the gap is not mistaken for an
oversight later: the Astrobee-specific FOV undistortion path (plumb\_bob
only), \texttt{ff\_msgs} (dead code even on the ROS1 side --- the node
advertises a publisher on this message type and immediately overwrites it
with the real \texttt{/pose} publisher on the next line, so nothing has ever
consumed it), and the producer/consumer image queue (one synchronous
callback instead).

\begin{warningbox}
A ROS2 (\texttt{ament\_cmake}) package must \textbf{not} live inside a
catkin (ROS1) workspace's source space. \texttt{catkin\_make} refuses to
configure a workspace containing any non-catkin package --- \texttt{"This
workspace contains non-catkin packages in it, and catkin cannot build a
non-homogeneous workspace without isolation"} --- so placing one there
breaks the ROS1 build of \emph{every} package in that workspace, not just
its own. A \texttt{CATKIN\_IGNORE} marker does not solve it either:
\texttt{colcon} honours that file too, so the marker fixes the ROS1 build by
hiding the package from the ROS2 build. The two build systems need entirely
separate source trees, which is one reason this whole document and its
folder are kept independent.
\end{warningbox}

\texttt{carolus\_ros2/} below is the same folder Section~\ref{sec:ros2-onto-blank-machine}
already cloned --- nothing new to fetch. \texttt{/path/to/raspberry5-carolus-ros2}
is the same placeholder explained there: substitute your own clone's actual
absolute path (e.g.\ \texttt{\textasciitilde/robotmaster/raspberry5-carolus-ros2}), do not
type it literally.

\begin{lstlisting}[style=shell]
# Host, Humble:
source /opt/ros/humble/setup.bash
mkdir -p ~/humble_ws/src && cd ~/humble_ws
ln -s /path/to/raspberry5-carolus-ros2/carolus_ros2 src/carolus_ros2
colcon build --packages-select carolus_ros2

# Host, Jazzy (no container --- Section~\ref{sec:ros2-jazzy-native-pc}'s case):
source /opt/ros/jazzy/setup.bash
mkdir -p ~/jazzy_ws/src && cd ~/jazzy_ws
ln -s /path/to/raspberry5-carolus-ros2/carolus_ros2 src/carolus_ros2
colcon build --packages-select carolus_ros2

# Inside the container (Jazzy), with this folder mounted at /carolus_ros2_ws:
source /opt/ros/jazzy/setup.bash
mkdir -p /colcon_ws/src
ln -s /carolus_ros2_ws/carolus_ros2 /colcon_ws/src/carolus_ros2
cd /colcon_ws && colcon build --packages-select carolus_ros2
\end{lstlisting}

\textbf{The middle block was missing until 2026-08-24} --- this section
showed the Humble-host and Jazzy-container recipes but never the
Jazzy-host one, even after Section~\ref{sec:ros2-jazzy-native-pc} started
covering that install path. A reader would have had to build it by analogy
from the Humble block; the pattern is identical, but nothing said so.

\textbf{Verified 2026-08-18, Jazzy}: clean build, 11.3\,s, zero warnings
attributable to the new code. \texttt{ldd} on the resulting binary, run with
the ROS2 environment sourced, resolves every dependency.

\textbf{Verified 2026-08-18, Humble, same host}: clean build, 7.45\,s, same
zero-warning result. The test in the next section produced byte-identical
output to the Jazzy run above (same contour count, same solver iteration
count and cost, matching pose fields to 11 significant digits --- the
remaining digit is Ceres iteration-order floating-point noise, not a real
difference) --- the same source, unmodified, compiled by two different ROS2
toolchains, ran the same detection and solve correctly on both.

\begin{warningbox}
\texttt{cv\_bridge}'s header is mid-rename across ROS2 distros
(\texttt{cv\_bridge.h} deprecated, \texttt{cv\_bridge.hpp} its replacement)
--- and \emph{which one a given install actually has is not predictable
from the distro name alone}. This project's Jazzy container only has
\texttt{.hpp}; its Humble install (22.04) only has \texttt{.h} --- confirmed
directly with \texttt{dpkg -L ros-humble-cv-bridge | grep cv\_bridge}, not
assumed from a changelog. \texttt{carolus\_node\_ros2.cpp} includes
whichever header actually exists (\texttt{\#if
\_\_has\_include(<cv\_bridge/cv\_bridge.hpp>)}) rather than hardcoding one
distro's answer --- if porting this pattern elsewhere, check the installed
package directly on the target machine first.
\end{warningbox}

\section{Testing it, without a robot}
\label{sec:ros2-synthetic}

A synthetic beacon frame stands in for a live camera.

\begin{lstlisting}[style=shell]

Four blobs, positioned by projecting the real beacon geometry through
\texttt{carolus\_node\_ros2.cpp}'s own compiled-in default intrinsics (not
the C920's calibrated values from Section~\ref{sec:ros2-realcam} --- this
test intentionally runs with no \texttt{--params-file}, so it must match
what the node assumes without one) at a plausible working range, published
on a loop to the node's subscribed topic:

\begin{warningbox}
\textbf{The four numbers on the next line are not a configuration file.}
They are literals inside a throwaway Python script, and they are the
\emph{RoboMaster S1's} intrinsics --- reproduced here only because they are
also \texttt{carolus\_node\_ros2.cpp}'s \texttt{declare\_parameter} defaults
(lines 57--60), which is what makes this test self-consistent when run with
no parameter file. Do not copy them for a webcam.

The actual parameter file is \texttt{logitech\_1080p.yaml} --- lowercase
\texttt{l} --- and it appears in Section~\ref{sec:ros2-realcam}, not here.
It carries entirely different values (\texttt{cx} 322.68 against 575.60,
\texttt{cy} 228.35 against 372.19: a quarter of the frame apart). Running
the real camera without it would silently produce badly wrong poses rather
than an error.
\end{warningbox}

\begin{lstlisting}[style=code]
import numpy as np, cv2
fx, fy, cx, cy = 546.1957, 547.0838, 575.6041, 372.1876
Z = 0.7
points_3d = [(0.0825,0,0), (-0.0825,0,0), (0,0.072,0), (0,0,0.0555)]
# Pick the blob colour FROM HSV, not guessed in BGR -- a saturated
# hand-picked BGR value easily lands too dark to clear the preprocessing
# threshold once converted to grayscale (this is why: the saturation
# findAndCalcContours needs for its own hue mask pulls luminance down,
# working against the brightness the initial threshold wants).
hsv = np.uint8([[[115, 90, 255]]])   # hue in this project's blue window (90-140)
bgr = cv2.cvtColor(hsv, cv2.COLOR_HSV2BGR)[0][0].tolist()
img = np.zeros((720, 1280, 3), dtype=np.uint8)
for X, Y, _ in points_3d:
    u, v = int(fx*X/Z + cx), int(fy*Y/Z + cy)
    cv2.circle(img, (u, v), 14, bgr, -1)
cv2.imwrite('synth_beacon.png', img)
\end{lstlisting}

Publish it on \texttt{/camera/color/image\_raw}, looping, at 10\,Hz
(\texttt{create\_timer(0.1, \ldots)} below). \textbf{This 10\,Hz is an
arbitrary choice for this test and measures nothing} --- it is not a
Carolus limit, and it is unrelated to the separately-measured 10\,Hz in
Section~\ref{sec:ros2-realcam}, which is the C920's own hardware ceiling at
1280x720. The two figures coinciding is a coincidence, and a confusing one;
raise this timer's rate freely if you want to push the node harder.

\begin{lstlisting}[style=code]
import rclpy, cv2
from rclpy.node import Node
from sensor_msgs.msg import Image
from cv_bridge import CvBridge

class SynthBeaconPublisher(Node):
    def __init__(self):
        super().__init__('synth_beacon_publisher')
        self.pub = self.create_publisher(Image, '/camera/color/image_raw', 10)
        self.bridge = CvBridge()
        self.frame = cv2.imread('synth_beacon.png')
        self.create_timer(0.1, self.tick)

    def tick(self):
        self.pub.publish(self.bridge.cv2_to_imgmsg(self.frame, encoding='bgr8'))

rclpy.init()
rclpy.spin(SynthBeaconPublisher())
\end{lstlisting}

Save as \texttt{publish\_synth\_beacon.py} in the same directory as
\texttt{synth\_beacon.png}, then, in separate terminals:

\begin{lstlisting}[style=shell]
python3 publish_synth_beacon.py
ros2 run carolus_ros2 carolus_node --ros-args -p image_threshold:=150
ros2 topic echo /pose --once
\end{lstlisting}

--once} run immediately after launching the publisher and the node
returned \texttt{WARNING: topic [/pose] does not appear to be published

is DDS discovery, not a real failure: \texttt{ros2 topic list} moments
later showed \texttt{/pose} present, and re-running the exact same
\texttt{echo --once} command then worked. If this happens, wait a couple of
seconds and retry --- it is not the QoS trap described next, which fails
\emph{every} time, not just the first.
\end{warningbox}

\begin{warningbox}
\texttt{image\_threshold:=150} is a test-only override for the synthetic
image above, not this project's real value (100, tuned for the physical
beacon --- see Section~\ref{sec:ros2-realcam}). Not arbitrary: the script's
HSV colour (115, 90, 255) converts to grayscale $\approx$184 (BGR
$(165,180,255)$, ITU-R BT.601 luma), so 150 clears the blob with margin while
the pure-black background (grayscale 0) still fails it --- computed, not
guessed, since the two targets need different thresholds for unrelated
reasons (this one is a colour-space computation, the real camera's is a
measured LED brightness). If a publisher process is already running, restarting the image
generator alone does \textbf{not} update what it sends --- a script that
loads the frame once at startup keeps serving the first version from memory
no matter how many times the file on disk changes. Restart the publisher,
not just the file.
\end{warningbox}

\subsection{QoS: the ROS2 failure that looks like success}

\begin{warningbox}
In ROS1 a subscriber connects to any publisher on the topic. In ROS2 it
connects only if the two QoS profiles are compatible, and an incompatible
pair delivers \textbf{nothing} --- no error, no warning, no log line. The
callback simply never fires and the node looks perfectly healthy. A
\textsc{reliable} subscriber specifically \emph{cannot} receive from a
\textsc{best effort} publisher --- the one QoS mismatch that silently drops
every frame rather than negotiating something that still works.
\end{warningbox}

\textbf{This specific driver does not trigger that trap, measured directly
rather than assumed:} \texttt{ros2 topic info /image\_raw --verbose} against
\texttt{ros-humble-usb-cam} 0.8.1 shows \texttt{Reliability: RELIABLE} ---
\emph{not} best effort. An earlier version of this section asserted ``camera
drivers normally publish best effort'' as a general claim; it was never
measured against this project's own driver, and the measurement contradicts
it. Both QoS profiles below were tested against the live C920 feed and both
received frames (\texttt{qos\_profile:=default}: 99 frames in 4\,s;
\texttt{qos\_profile:=sensor\_data}: 31 frames in 4\,s) --- verified
2026-08-20, not inferred from the general rule.

\textbf{The default is kept at \texttt{sensor\_data} anyway.} It is still
the strictly more compatible side --- a best-effort subscriber accepts
\emph{either} kind of publisher, so it can never be the thing that breaks
compatibility --- and the RoboMaster's own real camera bridge (not yet
tested through this ROS2 path) may turn out to publish best-effort, unlike
this one driver. \texttt{qos\_profile} stays overridable specifically so
that question can be tested directly against whatever publisher is in front
of it, rather than assumed either way.

\begin{center}
\begin{tabular}{@{}lll@{}}
\toprule
\textbf{\texttt{qos\_profile}} & \textbf{Reliability} & \textbf{Receives from} \\
\midrule
\texttt{sensor\_data} (default) & best effort & best-effort \emph{and} reliable publishers \\
\texttt{default}                & reliable    & reliable publishers only \\
\bottomrule
\end{tabular}
\end{center}

ros2 topic info /image_raw --verbose
\end{lstlisting}

\label{sec:ros2-realcam}

\end{lstlisting}

\textbf{Written for Humble only, same gap as the build recipes above ---
found again 2026-08-24.} On a native Jazzy host, substitute
\texttt{ros-jazzy-usb-cam ros-jazzy-rqt-image-view v4l-utils}; installed
and confirmed this way on the second bare-metal 24.04 machine (Chapter

already bundles its Jazzy equivalent into one command
(Chapter~\ref{ch:ros2-pi5}); this section never had one for a Jazzy host

Find the camera's actual device number first --- never assume it, a machine
with more than one video device (this one included) will not always put the
webcam at \texttt{/dev/video0}:

\begin{lstlisting}[style=shell]
v4l2-ctl --list-devices
\end{lstlisting}

\textbf{Standard step, every session, before launching \texttt{usb\_cam}:
fix the exposure.} Not conditional on seeing a problem first --- the factory
default is auto-exposure, which this project treats as a reliability defect
to close before it manifests, not a setting to leave alone until it causes
one:

\begin{lstlisting}[style=shell]
v4l2-ctl -d /dev/video0 --set-ctrl=auto_exposure=1
v4l2-ctl -d /dev/video0 --set-ctrl=exposure_time_absolute=40
\end{lstlisting}

\begin{warningbox}
\textbf{The exposure value is a per-room measurement, not a constant ---
\texttt{40}, not the \texttt{300} this section carried until 2026-09-03.}
Manual exposure alone is not enough: at \texttt{300} in a normally-lit lab,
\textbf{65\,\% of the frame} sat above the detector's brightness threshold
and the two largest blue-passing regions in the scene measured
\textbf{872\,px and 564\,px} against LED blobs of \textbf{10--35\,px} ---
ambient furniture and monitors were an order of magnitude larger than the
beacon, so blob selection locked onto the room instead of the target and the
solved range was wrong by tens of centimetres while every diagnostic still
read healthy.

\textbf{Measured 2026-09-03}, sweeping 20/40/80/150/299 on this camera in
this room: at 299, 106 blue clusters and 197\,882 bright pixels; at 40, the
four LEDs are the four largest objects in frame by a clear margin (35, 34,
25, 25\,px, next largest 17); at 20 an edge artefact (13\,px) outranks the
dimmest LED (12\,px), which is why 40 and not 20. \textbf{Re-measure this in
your own lighting} --- the correct value is the one where only four objects
survive, and the check is one frame's worth of blob areas, not a guess.
\end{warningbox}

\begin{lstlisting}[style=shell]
ros2 run usb_cam usb_cam_node_exe --ros-args \
    -p video_device:=/dev/video1 -p image_width:=640 -p image_height:=480 \
    -p pixel_format:=mjpeg2rgb -p framerate:=30.0
ros2 run rqt_image_view rqt_image_view /image_raw
\end{lstlisting}

\texttt{/dev/video1} above is what \texttt{v4l2-ctl --list-devices} reported
for this camera on this machine --- substitute whatever it reports on yours.

\begin{warningbox}
\textbf{Changed from a $1280\times720$/\texttt{yuyv2rgb} example to
$640\times480$/\texttt{mjpeg2rgb}, \texttt{2026-09-02}.} This is now the
standard resolution, not a cosmetic swap: the calibration below is only
valid at $640\times480$, and this camera offers Motion-JPEG at that
resolution (unlike some higher resolutions, where \texttt{usb\_cam}'s
default \texttt{mjpeg2rgb} silently falls back to raw YUYV --- see the next
warningbox, still relevant if a different resolution is ever used). The
$1280\times720$ measurements later in this section (the 10.000\,Hz
benchmark, the early detection tests) are kept as accurate records of that
now-superseded configuration, not the current recommended one --- do not
mix intrinsics calibrated at one resolution with a launch at the other.
\end{warningbox}

\begin{warningbox}
\texttt{pixel\_format:=yuyv2rgb} is not optional on a device whose target
resolution offers no Motion-JPEG mode (\texttt{usb\_cam}'s own default,
\texttt{mjpeg2rgb}, silently falls back to raw \texttt{yuv422\_yuy2} in that
case --- check with the driver's own printed format list). A raw YUYV
buffer reaching \texttt{carolus\_node} crashes it: \texttt{findAndCalcContours}
calls into \texttt{cv::findContours}, which requires \texttt{CV\_8UC1}, and a
2-channel packed YUV image is neither that nor the 3-channel BGR the
callback otherwise assumes. \texttt{ros2 topic echo <topic> --field encoding
--once} shows what a driver is actually publishing when in doubt.
\end{warningbox}

\begin{warningbox}
\textbf{Why the exposure step above runs \emph{before} \texttt{usb\_cam},
not as a \texttt{usb\_cam} parameter.} \textbf{Verified 2026-08-31}, on the
second bare-metal 24.04 machine (Section~\ref{sec:ros2-jazzy-native-pc}):
\texttt{usb\_cam}'s own \texttt{autoexposure}/\texttt{exposure} ROS
parameters silently do nothing on this camera --- the node's own startup log
reads \texttt{Setting 'exposure\_auto' to 3} immediately followed by
\texttt{unknown control 'exposure\_auto'}. \texttt{usb\_cam} targets the
older V4L2 control name (\texttt{exposure\_auto}), while this camera's
driver only exposes the newer one (\texttt{auto\_exposure}, confirmed via
\texttt{v4l2-ctl -d /dev/video0 --list-ctrls}). The parameter is accepted,
logged, and has no effect --- no error surfaces anywhere in the ROS graph,
which is exactly why this cannot be left as a \texttt{usb\_cam} launch
argument: it would silently fail every time.

\texttt{auto\_exposure=1} is this control's manual mode (\texttt{3} is the
factory default, Aperture Priority / auto).
\texttt{exposure\_time\_absolute} then becomes settable (it reports
\texttt{flags=inactive} while auto mode is on) --- range \texttt{3--2047} on
this camera, factory default \texttt{250}.

\textbf{Verified 2026-08-31, before/after, same camera, same beacon, 10\,s
each:} both the factory auto-exposure default and the fixed manual value
above detected the beacon on all 285/285 frames processed
(\texttt{converged=1} throughout). The fix did not correct a live detection
failure in this test --- \texttt{final\_cost} was, if anything, marginally
tighter under manual exposure (84.3--85.0 vs.\ 82.9--84.9 under auto)
consistent with removing one source of frame-to-frame variance, but neither
run is quotable as decisive from a single 10 s session. It is kept as the
standard regardless: auto-exposure remains a documented risk (a prior
intern's report on the same camera model describes it causing intermittent
detection failure under different lighting) that costs nothing to close
pre-emptively.
\end{warningbox}

\begin{warningbox}
\textbf{Lowest cost is not sufficient to pick the winner --- two of the 24
candidates are mirror images.} $P_1=(0.0825,0,0)$ and $P_2=(-0.0825,0,0)$
sit symmetrically about the beacon's own $x=0$ plane, so the assignment
that swaps them is a reflection of the assumed geometry. It converges as
cleanly as the truth, reports the same distance to within 0.3\,mm, and
flips the sign of $Z$. \textbf{Measured} 2026-09-04, beacon dragged around
a 30\,cm square at $\sim$1\,m: the winning candidate switched from 15 to 14
once and never switched back, $Z$ going from $-0.99$\,m to $+0.99$\,m for
the rest of the recording. Warm-start makes it permanent rather than
intermittent --- the prior-refresh guard checks only whether Ceres
converged, which the mirrored solution does.

Since 2026-09-04 the node applies a \textbf{cheirality check}: any
candidate placing the beacon behind the camera ($t_z \geq 0$) is skipped.
The test sits \emph{inside} the candidate loop, before a winner is
selected --- rejecting after selection would discard a usable frame every
time the mirror had the lower cost, rather than letting the correct
candidate take it. The single-guess path (\texttt{multi\_hypothesis\_sort:
false}) gets the same test as a backstop, but has no runner-up, so a
rejected frame publishes nothing and logs an error.

\textbf{Verified} 2026-09-04 on the Pi 5: 3037 poses tracing a 30\,cm square (edges measured 28.8--33.2\,cm,
corners square to within 4\textdegree{}, straightness 2--7\,mm RMS), six different candidates winning, \textbf{zero} wrong-signed
samples --- and candidate 14, the culprit above, still won 331 frames
legitimately. The filter disqualifies wrong-signed \emph{solutions}, not
candidate numbers.

\textbf{The convention is empirical}: here, a beacon in front of the camera
reports $t_z<0$. Port this to a pipeline with the opposite convention and
the test inverts --- the symptom being a node that converges on every frame
and publishes none.
\end{warningbox}

\textbf{One field needs a real YAML list, not a string:}
\texttt{known\_points} must be \texttt{[0.0825, 0.0, 0.0, ...]}, a literal
list --- \texttt{declare\_parameter} has no string-to-vector parsing for a
\texttt{std::vector<double>} default, and a quoted string either fails to
load or silently mismatches the declared type.

\begin{warningbox}
\textbf{A second silent failure, this one undetectable from the log.}
\texttt{cv\_bridge::\allowbreak toCvShare(msg,\allowbreak\ msg->encoding)}
returns whatever encoding
the source publishes --- against this driver, \texttt{rgb8}, not
\texttt{bgr8}. Converting RGB data with \texttt{cv::COLOR\_BGR2HSV} swaps red
and blue going into the hue calculation: no crash, no warning, every hue
silently rotated. A real blue-LED beacon can land clean outside
\texttt{lb\_hue}/\texttt{ub\_hue} as a direct result, and the node keeps
publishing \texttt{"0 contours found"} on schedule --- identical to the
correct output when no beacon is in frame. Fixed by requesting
\texttt{"bgr8"} explicitly from \texttt{cv\_bridge::toCvShare}, not the
source encoding: the conversion becomes \texttt{cv\_bridge}'s job for
whatever a given driver publishes, not an assumption baked into this
callback.
\end{warningbox}

\begin{warningbox}
\textbf{Hue is on OpenCV's 0--180 scale, not 0--360 --- and getting this
wrong kills every detection while the node looks healthy.} OpenCV stores
hue on half the usual circle, so the profile's
\texttt{lb\_hue}\,\texttt{:}\,\texttt{90.0} and
\texttt{ub\_hue}\,\texttt{:}\,\texttt{140.0} select blue. Enter the values
from the 0--360 convention a colour picker gives you --- 240 for blue --- and
\emph{every} blob is rejected: the node starts, subscribes, processes every
frame and publishes \texttt{"0 contours found"} on schedule, which is
byte-for-byte what it prints when no beacon is in front of it.

Rough reference points on the 0--180 scale: red $\approx$ 0--10 and
170--180, green $\approx$ 35--85, blue $\approx$ 90--130. Halve any
0--360 figure before entering it here.

This is the same trap as the encoding bug above, arrived at from the other
direction: there, the hue was rotated correctly-but-wrongly by an RGB/BGR
swap; here, the window it is compared against is on the wrong scale. Both
produce an identical, entirely healthy-looking log.
\end{warningbox}

\textbf{Verified 2026-08-20}: Logitech HD Pro Webcam C920, 1280x720, measured
10.000\,Hz average (std dev 0.00392\,s, 30-sample window --- this device
offers only 10\,FPS at this resolution, confirmed against its own format
list; 30\,FPS exists only at 640x480 and below). \texttt{carolus\_node}
processes every frame with no crash, and reports \texttt{"0 contours found"}
with no beacon in view --- the correct result, not a failure.

\textbf{With a lit beacon in frame, same session:} four blobs found,
\texttt{SortTargets\allowbreak UsingTetrahedron\allowbreak Geometry}
succeeded, the Ceres solve ran,
and a \texttt{geometry\_msgs/msg/PoseStamped} was published on \texttt{/pose}
with a correctly normalised quaternion. \textbf{One parameter change was
required to get there}, and it is not optional on this camera:

\begin{lstlisting}[style=shell]
ros2 run carolus_ros2 carolus_node --ros-args \
    --params-file carolus_ros2/config/logitech_1080p.yaml \
    -p image_threshold:=100
\end{lstlisting}

\begin{warningbox}
\textbf{A lit blue beacon can sit far below \texttt{image\_threshold} while
being perfectly correct in hue and saturation.} Measured on a real frame
grabbed off \texttt{/image\_raw}: the LEDs read hue 105--115 (well inside the
90--140 window) and saturation 200--255 (well above the 80 floor), but their
\emph{grayscale} value peaks at \textbf{131} --- under the default
\texttt{image\_threshold} of 190, so \texttt{preprocessImage} discards them
before the hue mask ever runs. Saturated blue converts to a low grayscale
value under the standard luminance weighting, where blue's coefficient is
smallest. The symptom is \texttt{"0 contours found"} on every frame with a
beacon plainly visible in \texttt{rqt\_image\_view}.

Do not guess a replacement value: grab one frame and measure. Moving the
beacon closer does \emph{not} fix it (tested --- still zero contours at
threshold 190), because the ceiling is luminance, not blob size.
\texttt{image\_threshold:=100} worked for this camera and this beacon,
confirmed again on the Pi 5 (Chapter~\ref{ch:ros2-pi5}) against the same
physical camera --- now \texttt{logitech\_1080p.yaml}'s baked-in default
rather than a per-launch override, since both measurements agree. A
different camera or beacon still needs its own measurement, not this value
assumed.
\end{warningbox}

\begin{warningbox}
\textbf{Detection working does not mean the pose is trustworthy.} Every solve
in this test reported \texttt{converged=0} (Ceres hit
\texttt{max\_num\_iterations=30} without converging), and the pose is written
\emph{unconditionally} --- a non-converged solve returns a finite, plausible
pose that is indistinguishable from a good one unless the diagnostic fields
are read. Two \texttt{/pose} reads taken at two visibly different beacon
positions returned translations a few centimetres apart
(\texttt{(4.232, 2.957, -7.476)} then \texttt{(4.201, 2.939, -7.444)}), which
is not what a solver tracking a moved target produces.

\textbf{The cause was found and fixed on 2026-08-25} ---
Section~\ref{sec:bug132}. The readings above are kept as the dated record of
what this test showed \emph{before} that fix; do not use them as current
values. \texttt{converged=1} after it.
\end{warningbox}

\section{Why a Pi 5, and why aarch64 matters here}

Two things this chapter exists to test that the lab-PC chapter could not:
whether the extracted core (Chapter~\ref{ch:ros2-labpc}'s claim) is genuinely
architecture-independent, not just toolchain-independent --- everything
verified so far ran on x86\_64 --- and whether ROS2 Jazzy runs
\emph{natively}, without the Docker layer the lab PC needed because its host
OS is 22.04, not 24.04. The Pi 5 can run Ubuntu 24.04 directly, which is
Jazzy's own native target.

\section{Installing Ubuntu 24.04 and ROS2 Jazzy, natively}

\textbf{Status: inherited, not executed by this project.} This board arrived
with Ubuntu 24.04.4 LTS and ROS2 Jazzy already installed and sourced (a prior
Carolus ROS2 attempt on this same Pi, confirmed by the board's owner --- see
Section~\ref{sec:ros2-pi5-webcam}). The commands below are the from-scratch

\begin{warningbox}

\section{Against the webcam}
\label{sec:ros2-pi5-webcam}

\textbf{Status: Verified 2026-08-21}, including a real beacon detected and
\texttt{/pose} published (see the success criteria at the end of this
section). \textbf{Not verified}: pose accuracy on this board since the
2026-08-25 solver fix (Section~\ref{sec:bug132}) --- the pose values quoted
below predate it and are kept as a dated record, not as current values.

This is the same physical camera as the lab PC chapter (a Logitech HD Pro
Webcam C920) and the same config file,
\texttt{carolus\_ros2/\allowbreak config/\allowbreak logitech\_1080p.yaml}
--- it holds this camera's calibrated intrinsics and the beacon's known
geometry. Reused here unmodified, on purpose: if this board's detection
behaves differently from the lab PC's, that difference is then attributable
to the board, not to a re-tuned parameter.

Find the camera's actual device number first --- do not assume it carries
over from another machine:

\begin{lstlisting}[style=shell]
v4l2-ctl --list-devices
\end{lstlisting}

\textbf{Standard step, every session, before launching \texttt{usb\_cam}:
fix the exposure.} This camera's factory default is auto-exposure, which
this project treats as a reliability defect to close before it manifests.
\texttt{usb\_cam}'s own ROS-level \texttt{autoexposure}/\texttt{exposure}
parameters do not work on this camera model --- they target the older V4L2
control name \texttt{exposure\_auto}, while this camera's driver only
exposes the newer \texttt{auto\_exposure} (confirmed on the lab PC via
\texttt{v4l2-ctl -d /dev/video0 --list-ctrls}; \textbf{not separately
re-confirmed on this Pi's own V4L2 stack}, since it is a property of the
camera's own firmware rather than the host). The ROS-level parameter is
accepted, logged, and silently does nothing --- which is exactly why the fix
has to run outside \texttt{usb\_cam}, before it starts, not as one of its
launch arguments:

\begin{lstlisting}[style=shell]
v4l2-ctl -d /dev/video0 --set-ctrl=auto_exposure=1
v4l2-ctl -d /dev/video0 --set-ctrl=exposure_time_absolute=40
\end{lstlisting}

\begin{warningbox}
\textbf{\texttt{40} is a per-room measurement, not a constant} --- and
manual exposure alone is not sufficient. Measured on the lab PC's identical
camera 2026-09-03: at \texttt{300}, 65\,\% of the frame cleared the
brightness threshold and the two largest blue regions in the scene were
872\,px and 564\,px against LED blobs of 10--35\,px, so blob selection
locked onto room furniture rather than the beacon while every log line still
looked healthy. At \texttt{40} the four LEDs were the four largest objects
in frame (35, 34, 25, 25\,px, next largest 17). Re-measure in your own
lighting: the right value is the one where only four objects survive, and
one frame's blob areas answer it. \textbf{Not re-measured on this board
specifically} --- the sweep was run on the lab PC.
\end{warningbox}

\begin{lstlisting}[style=shell]
ros2 run usb_cam usb_cam_node_exe --ros-args \
    -p video_device:=/dev/video0 -p image_width:=1280 -p image_height:=720 \
    -p pixel_format:=yuyv2rgb
ros2 run rqt_image_view rqt_image_view /image_raw
ros2 run carolus_ros2 carolus_node --ros-args \
    --params-file carolus_ros2/config/logitech_1080p.yaml \
    -p image_threshold:=100
\end{lstlisting}

\texttt{/dev/video0} above is what \texttt{v4l2-ctl --list-devices} reports
for the webcam on this Pi --- not the lab PC's \texttt{/dev/video1}, device
enumeration is host-specific.

\begin{warningbox}
This Pi's own ISP (\texttt{pispbe}/\texttt{rpivid}) occupies
\texttt{/dev/video19-37} --- a plain \texttt{ls /dev/video*} lists 21
devices, and the webcam is easy to misidentify among them without running
\texttt{v4l2-ctl --list-devices} to see which one is actually named
``HD Pro Webcam C920''.
\end{warningbox}

\texttt{image\_threshold:=100}, not the RoboMaster profile's default 190,
carried over from the lab PC rather than independently re-derived from a
pixel measurement on this board. The reason 190 fails on this camera class
at all: a saturated blue LED carries little weight in the standard
$0.299R+0.587G+0.114B$ grayscale conversion, so a blue LED that looks
plainly bright to the eye can still land low in grayscale --- measured on
this exact camera at 105--115 hue, 200--255 saturation (both comfortably
inside their detection windows), but only 131 grayscale, under the 190
threshold. 100 sits below that measured ceiling with margin. Not
independently re-measured on this Pi's own copy of the LEDs, but confirmed
to work here unchanged: detection succeeded with this value, see the
success criteria at the end of this section.

\textbf{Verified 2026-08-21}: \texttt{usb\_cam\_node\_exe} publishes real
1280x720 \texttt{rgb8} frames on \texttt{/image\_raw} (confirmed with
\texttt{ros2 topic echo /image\_raw --once}, live pixel data, not just topic
presence), logging \texttt{image subscription QoS profile: sensor\_data (best
effort)} and \texttt{carolus\_ros2 up, camera\_topic=/image\_raw} on startup.

\begin{warningbox}
\textbf{This node uses a plain \texttt{rclcpp} subscription, not
\texttt{image\_transport}.}
\texttt{image\_transport::\allowbreak create\_subscription}'s
``raw'' transport plugin does not reliably deliver frames on this board ---
verified against a plain
\texttt{create\_subscription<\allowbreak sensor\_msgs::\allowbreak msg::\allowbreak Image>},
which does. Since this node only ever used the ``raw'' transport (no
compression, no other \texttt{image\_transport} feature), the dependency is
dropped entirely rather than left unused --- absent from
\texttt{CMakeLists.txt} and \texttt{package.xml}.
\end{warningbox}

\textbf{Re-verified on the lab PC (Humble, Chapter~\ref{ch:ros2-labpc})}:
\texttt{colcon build --packages-select carolus\_ros2} against
\texttt{/opt/ros/humble} (native, no container needed there --- Ubuntu 22.04
is Humble's own target) --- 16.8\,s / 17.8\,s real, 0 compiler warnings.
Runtime not re-confirmed: no webcam was attached to the lab PC at the time.

\section{Maximum update rate, measured}
\label{sec:ros2-maxrate}

Every rate this project had observed before 2026-08-22 was bounded by the
camera, not by Carolus: the C920 offers only 10\,FPS at 1280x720. To measure
the node itself the input has to stop being the limit, so
\texttt{bench\_carolus\_rate.py} publishes synthetic four-blob frames as fast
as it can and compares \texttt{/pose} against its own achieved rate.

\textbf{Measured 2026-08-22}, 1280x720, full path including the Ceres solve,
30\,s after a 3\,s discarded warm-up:

\begin{warningbox}
\textbf{$^\dagger$ Row 4 is not bare metal, and reads lower for a reason
that has nothing to do with Jazzy, Humble, or containers.} No spare 24.04
x86\_64 hardware was available, so this row comes from Ubuntu 24.04 +
ROS2 Jazzy installed with no container inside a QEMU/KVM virtual machine on
the same lab PC, measured while the host itself carried a load average of
1.53 from unrelated work running concurrently. A hypervisor adds real
overhead beyond a container's near-zero one (trap-and-emulate, virtio I/O),
and a shared, non-idle host compounds it. \textbf{Do not read row 4 against
row 3 as "native is slower than a container"} --- the 71.8\,Hz gap is far
more plausibly virtualisation and host contention than architecture. This
row is the best proxy available without dedicated 24.04 hardware; a
bare-metal run should replace it if such a machine becomes available.

\textbf{$^\ddagger$ Row 5, measured 2026-08-24, is genuine bare metal
(\texttt{systemd-detect-virt} confirms \texttt{none})} --- a second,
dedicated 24.04 machine (Dell, Intel Core i5-7500 @ 3.40\,GHz, 4 cores),
this section's install and build followed literally, no container, no VM.
It settles Hector's Q1/Q2 as cleanly as this project can: native install on
real 24.04 hardware works, unmodified. \textbf{It is still not a clean
architecture comparison against rows 1--3}, for reasons that have nothing
to do with virtualisation this time: the CPU is a 2017-era part, markedly
older than whatever powers row 1--3's machine, and \texttt{uptime} showed a
load average of 1.49 with four other users logged in during the
measurement --- real, understood confounds, not a mystery. What the
near-identical number to row 4's 204.1\,Hz shows is that the VM caveat in
row 4 was the right call: two completely different confounds (hypervisor
overhead vs.\ an older, shared CPU) landing on nearly the same figure is
coincidence, not evidence that either confound was actually negligible.
\end{warningbox}

So Carolus sustains roughly \textbf{265\,Hz} on the lab PC while the camera
delivers 10 --- the observed rate is camera-bound by a factor of about 26,
and no realistic camera would make the node the limit. \textbf{The Pi 5 row,
measured 2026-08-22}, is genuinely lower: 52.8\,Hz, still with 51\,\%
headroom over its own harness so the number is real, not an artefact of a
Python publisher too slow to say otherwise (this board's 4-core Cortex-A76 is
the harness's own bottleneck too, at roughly 103\,Hz rather than the lab PC's
~650\,Hz --- the two are not on the same footing, and the lab PC's 40\,\%
headroom was measured against a considerably faster harness). A 5x gap
between a quad-core ARM board and an x86\_64 desktop for a Ceres-solve-bound
workload is unsurprising and still leaves the Pi 5 roughly 5x faster than the
10\,Hz the camera ever delivers.

Rows 1 and 2 are the only pair that isolates containerisation, being the same
distribution either side of the boundary: \textbf{+0.6\,\%, no measurable
cost}. Row 3 differs in two variables at once (distribution and container)
and should not be read as a Jazzy-versus-Humble result. Rows 4 and 5 each
differ from rows 1--3 in ways that have nothing to do with the middleware
(hypervisor overhead for row 4; a markedly older, shared CPU for row 5 ---
see both warnings above) and should not be read against rows 1--3 as a
clean performance comparison. What rows 4 and 5 \emph{do} establish
cleanly, each on its own terms, is that native install works: row 4
end-to-end inside a VM, row 5 on genuine bare metal.

Detection alone, with no beacon in frame so the solver never runs, reached
458.2\,Hz on the lab PC (native), with contour extraction at 0.258\,ms mean
over 400 samples; on the Pi 5, roughly 57.5\,Hz by counting processed-frame
log lines rather than the script's own instrumented method (\texttt{/pose}
never publishes with no beacon, so there is nothing for the built-in
headroom check to compare against). The lab PC's gap between detection-only
and full-solve is a clean 1.7x; the Pi 5's is only about 1.1x, which is more
consistent with the weaker board's own Python-harness ceiling limiting the
detection-only figure than with the solve itself costing less there --- this
number is reported with that caveat, not as clean as the lab PC's. The
second PC's own detection-only figure, measured the same way as the Pi 5's
(log-line counting, since \texttt{/pose} again never publishes), reached
354.1\,Hz against a 203.7\,Hz full-solve --- a clean 1.74x ratio, consistent
with row 1's 1.7x despite the very different hardware, which is a useful
cross-check that the underlying cost structure (solve dominates, detection
is cheap) holds regardless of which machine is doing the work.

\begin{warningbox}
\textbf{A benchmark of this shape measures the publisher unless it proves
otherwise.} If the harness cannot outrun the node, \texttt{/pose} simply
matches the input and the harness's own rate gets recorded as though it were
the node's ceiling. The script therefore measures its own rate as well and
\emph{refuses} to report a maximum when the two come within 15\,\% of each
other. On its first use it returned
\texttt{IMPLAUSIBLE -- /pose (238.2\,Hz) exceeds input (165.3\,Hz)}: a
container left running from an earlier configuration still had its own node
publishing, with DDS discovery crossing Docker's default bridge. Without that
guard the number would have been written down as a result.
\end{warningbox}

\chapter*{Known Limitations}
\addcontentsline{toc}{chapter}{Known Limitations}

\textbf{Detection is proven on both targets. Pose accuracy is not, on
either.} This applies across the whole document, not just one chapter:

\begin{center}
\begin{tabular}{@{}p{0.30\textwidth}p{0.30\textwidth}p{0.30\textwidth}@{}}
\toprule
 & \textbf{Lab PC (Humble)} & \textbf{Raspberry Pi 5 (Jazzy)} \\
\midrule
Beacon detected, \texttt{/pose} published & yes & yes \\
\addlinespace
Ceres \texttt{converged} & 0, every solve & 0, every solve \\
\addlinespace
Direct evidence of inaccuracy & yes --- two visibly different beacon
positions gave poses a few cm apart & \textbf{yes, see below} \\
\bottomrule
\end{tabular}
\end{center}

\texttt{ceresP4P.cpp} hits \texttt{max\_num\_iterations=30} without
converging on either target, and the pose is written \emph{unconditionally}
--- a non-converged solve returns a finite, plausible-looking pose that is
indistinguishable from a correct one unless \texttt{converged}/%
\texttt{final\_cost}/\texttt{iterations} are read directly. The Pi 5's pose
matches the lab PC's own recorded value to within a few centimetres, which
confirms the two ports agree with \emph{each other} --- not that either is
numerically correct, since nothing in this document establishes ground
truth.

\textbf{Measured 2026-08-22, Pi 5, 38 consecutive \texttt{/pose} samples over
a few seconds, beacon not deliberately moved during the capture:} the
readings do not sit at one value with sensor noise around it. They cycle
through roughly five distinct clusters, several centimetres apart,
repeatedly returning to the same clusters rather than drifting --- e.g.\
$(4.247, 2.975, -7.491)$, $(4.217, 2.953, -7.459)$, $(4.210, 2.949, -7.451)$,
$(4.260, 2.990, -7.501)$, interleaved frame to frame with no beacon movement
to explain the jumps. \texttt{max distance} (the point-correspondence sort's
own diagnostic) alternated between approximately 98 and 353 across
consecutive frames while \texttt{final\_cost} stayed in a narrow 21--24 band
--- the signature of the sort landing on a different correspondence each
time rather than of a single stable fit degrading. This is new evidence for
the same conclusion the lab PC's 20 August displacement test already
pointed to, from an independent angle: \textbf{a solver or correspondence
instability, not a calibration bias}, since a miscalibrated-but-stable
camera would not produce discrete jumps with the target undisturbed. Also
worth noting plainly: $z\approx-7.5\,$m is not a physically plausible depth
for an indoor desk setup, which is a further sign that these numbers are not
close to correct regardless of cause.

\textbf{Measured 2026-08-22, Pi 5, a real controlled displacement --- the
decisive test.} The physical beacon was measured with a ruler at
89\,cm (its off-plane LED) / 94\,cm (the other three) from the camera;
\texttt{/pose} was captured over several seconds and found rock-stable
($x{=}4.2507$, $y{=}2.9736$, $z{=}-7.4884$, agreeing to five decimal places
across 44 samples --- a different behaviour from the discrete jumps above,
noted rather than reconciled: two distinct instability symptoms have now
been observed on two occasions, not one explained mechanism). The beacon was
then moved straight back by a further \textbf{measured 30\,cm} with the
camera untouched. \texttt{/pose} was captured again, equally stable at its
new value ($x{=}4.2528$, $y{=}2.9750$, $z{=}-7.4919$, 5 samples). The
resulting change:

\begin{center}
\begin{tabular}{@{}lr@{}}
\toprule
Real physical displacement (measured) & 300\,mm \\
\texttt{/pose} displacement (computed from the two means) & 4.28\,mm \\
Fraction of the real displacement reflected & \textbf{1.43\,\%} \\
\bottomrule
\end{tabular}
\end{center}

A camera that is merely miscalibrated still responds to a real 300\,mm move
--- wrong scale, wrong sign, offset, but a response of the right order of
magnitude. \textbf{A response of 1.43\,\% is not a calibration error; it is
the absence of a response.} This settles the question directly rather than
by inference: recalibrating this camera cannot be expected to fix pose
accuracy on its own, because the pose is not meaningfully reacting to the
beacon's real position in the first place.

\textbf{The cause was found on 2026-08-25 and is fixed
(Section~\ref{sec:bug132}): a missing normalized-to-pixel conversion, not
calibration.} Everything above is the dated record of the measurement that
led there. \textbf{Do not report a pose as accurate until this exact test is
re-run with the fixed binary} --- the fix is verified against a synthetic
image only.

\textbf{Reproduced 2026-08-24 on a third machine, third physical beacon,
third camera unit, real distance 60\,cm} --- the discrete-jump symptom
again (12 samples, several clusters, \texttt{max distance} again
alternating between multiple values with outright sort failures
interleaved), landing suspiciously close to the Pi 5's own numbers despite
nothing physical matching between the two setups. \textbf{Checked before
being written up as independent confirmation:} \texttt{known\_points} is
the identical, shared, already-flagged-unverified beacon geometry on every
machine tested against a real camera so far. An identical wrong geometry
applied identically everywhere is a live, undismissed explanation for why
outputs cluster similarly --- so this observation is
\textbf{corroborating, not independently decisive}, unlike the 30\,cm
displacement test above, whose conclusion does not depend on
\texttt{known\_points} being correct: a geometry mismatch predicts a pose
at the wrong scale, not one that fails to respond to a real 300\,mm move
at all.

\textbf{That measurement was taken the same day, on today's beacon
specifically.} All six pairwise LED-to-LED distances were measured with a
tape measure and checked against what \texttt{known\_points} predicts
(side-to-side 16.50\,cm, each side to the top LED 10.95\,cm, each side to
the off-plane LED 9.94\,cm, top to off-plane 9.09\,cm) --- \textbf{matched
to within 0.1--0.2\,cm}, the tape measure's own resolution limit rather
than a real discrepancy. \texttt{known\_points} is confirmed correct for
\emph{this} beacon, which rules out a geometry mismatch as the explanation
for what was observed on it. \textbf{Not yet done:} the same check on the
Pi 5's own beacon and the RoboMaster's --- different physical units, not
covered by this result.

\subsection{Root cause found and fixed --- 2026-08-25}
\label{sec:bug132}

\textbf{The pose error above was one missing loop.} After sorting, the four
points must be pushed back into \textbf{pixel} space before the solver sees
them. The ROS1 node does this; the ROS2 node did not, so
\texttt{ReprojectionErrorWithAnalyticDiff} was subtracting a \emph{unit
bearing vector} component (magnitude ${\sim}0.1$) from a \emph{pixel}
prediction (\texttt{xp*fx + cx}, dominated by $c_x{\approx}576$,
$c_y{\approx}372$). \textbf{Measured} at the exact true pose: residuals of
372--640 instead of ${\sim}0$. Minimising that drives the pose toward
cancelling $c_x$/$c_y$ --- values shared by all four points and independent
of where the beacon is --- which is why \texttt{/pose} barely moved when the
beacon did.

The fix, in \texttt{carolus\_node\_ros2.cpp} immediately after the sort:

\begin{lstlisting}[style=code]
const double k_fx = camera_matrix_.at<double>(0, 0);
const double k_fy = camera_matrix_.at<double>(1, 1);
const double k_cx = camera_matrix_.at<double>(0, 2);
const double k_cy = camera_matrix_.at<double>(1, 2);
for (auto& p : sorted) {
    p(0) = p(0) * k_fx + k_cx;
    p(1) = p(1) * k_fy + k_cy;
}
\end{lstlisting}

\textbf{Measured, before and after, on this node against the identical
synthetic beacon} (Section~\ref{sec:ros2-synthetic}; ground truth
$(0,0,0.700)$, pre-fix state recovered by rebuilding the previous source,
not recalled):

\begin{center}
\begin{tabular}{@{}lrrr@{}}
\toprule
 & pre-fix & post-fix & truth \\
\midrule
\texttt{/pose} $x$ & 7.4003 & 0.0008 & 0.000 \\
\texttt{/pose} $y$ & 4.7602 & $-0.0041$ & 0.000 \\
\texttt{/pose} $z$ & $-6.9921$ & $-0.6794$ & $\pm0.700$ \\
$|t|$ & \textbf{11.40\,m} & \textbf{0.679\,m} & 0.700\,m \\
\texttt{final\_cost} & 27.5911 & 50.3195 & --- \\
\texttt{iterations} & 31 & 18 & --- \\
\texttt{converged} & \textbf{0} & \textbf{1} & --- \\
\bottomrule
\end{tabular}
\end{center}

The residual 2.9\,\% is the synthetic image's own quantisation --- it draws
blobs at \texttt{int(fx*X/Z + cx)}, so up to half a pixel of error is in the
input before Carolus sees it.

\begin{warningbox}
\textbf{\texttt{final\_cost} went UP while the pose became correct}
(27.6 $\rightarrow$ 50.3). Do not use it as a quality gate. Relatedly, the
\texttt{converged=0} that every run of this node had ever reported was a
\emph{symptom} of this bug, not a separate solver-tuning problem: a residual
that cannot reach zero hits the 30-iteration cap by construction.
\end{warningbox}

\subsection{Hardware validation, and a second real defect found in the process --- 2026-08-25}
\label{sec:bug088}

The 30\,cm displacement test was re-run the same day, second 24.04 PC, real
beacon. \textbf{It did not initially confirm the fix} --- and the reason why
is itself worth documenting, since the next person to run this test will hit
the same trap if they don't know about it.

\textbf{Attempt 1, independent restarts at each distance:} beacon at 60\,cm,
20 samples, mean $(-0.2739,-0.2887,-0.8726)$; moved a real 30\,cm, node
restarted, 20 more samples, mean $(-0.3696,-0.2176,-0.7574)$.
$|\Delta t| = 165.8$\,mm of 300\,mm (55.3\,\%) --- but $z$ moved the
\textbf{wrong direction} (magnitude \emph{decreased} as the beacon moved
farther away), which is not what a scale error looks like.

\textbf{Checking each point's own stability found why.} A new tool,
\texttt{capture\_pose\_stats.py --cluster}, groups samples into clusters
over time. 40 stationary samples at 60\,cm gave \textbf{8 distinct
clusters}, two dominant (19 and 12 of 40) alternating almost every 1--3
frames --- \textbf{BUG-131's correspondence-sort instability, reproduced
live}, and shown to be \textbf{geometry-dependent rather than a narrow
edge case}: the same rig at 90\,cm and 120\,cm was rock-stable (std under
0.6\,mm), each in its \emph{own} disconnected local minimum. Two
independently-stable readings 30\,cm apart still disagreed by 135\,mm with
$z$ backwards.

\begin{warningbox}
\textbf{A before/after pair proves nothing unless both readings are
confirmed to be in the same correspondence-sort regime.} Cluster-check each
position first. An arbitrarily-chosen real distance (60\,cm here, no special
reason) can land inside an unstable zone with no warning besides the check
itself.
\end{warningbox}

\textbf{Root cause: BUG-088, implemented the same session.}
\texttt{ceresP4P.cpp} solves every frame from the identical fixed starting
vector, no memory of the previous frame --- so a different starting geometry
is free to fall into a different, unrelated local minimum. Fixed by warm-
starting from the last \textbf{converged} solve:
\texttt{computeAndValidatePosesWithRefinement} gained a trailing
\textbf{optional} \texttt{initial\_guess} parameter (existing callers passing
none keep the old fixed-start behaviour, verified unchanged); the ROS2 node
gained a \texttt{warm\_start} parameter (default \texttt{true};
\texttt{-p warm\_start:=false} for a direct A/B on the same binary).

\begin{warningbox}
\textbf{A units mismatch was found while wiring this up, independent of
whether the fix is correct.} \texttt{bestPose.R} is computed from
\texttt{camera\_params[3..5]} via \texttt{computeRotationMatrix}, which
treats them as \textbf{Euler angles}. Ceres's own cost function treats the
\emph{identical} three numbers as an \textbf{AngleAxis} vector. Sidestepped,
not fixed: the raw solved vector is now stored directly
(\texttt{CameraPose::solved\_params}) instead of being re-derived from $R$.
\end{warningbox}

\textbf{Verified synthetically first}, same discipline as BUG-132: stationary
target, first frame unchanged (\texttt{iterations=18}, no prior yet), every
frame after \textbf{\texttt{iterations=1, converged=1}}, identical
\texttt{final\_cost} and \texttt{/pose} to the bit. Warm-starting from an
already-correct answer costs nothing.

\textbf{Verified live: a cold restart still lands on the same answer as
before the change} (120\,cm, 30 samples: $(-0.3375,-0.1935,-0.6253)$ against
the pre-fix $(-0.3388,-0.1939,-0.6280)$, agreement to 2.7\,mm) ---
warm-starting changes nothing about \emph{where} an independent solve
converges, only what happens after.

\textbf{The decisive test: the beacon moved without restarting the node.}
90\,cm, node left running from the 120\,cm state, 30 samples, \textbf{29 of
30 in one cluster}: mean $(-0.3844,-0.2450,-0.8284)$.
$|\Delta t| = 213.7$\,mm of 300\,mm = \textbf{71.2\,\%}, and, for the first
time this session, \textbf{$z$ moved in the physically correct direction}
(the beacon moved closer; $|z|$ increased).

\begin{center}
\begin{tabular}{@{}lrrr@{}}
\toprule
 & independent restarts & warm-started, no restart & \\
\midrule
$|\Delta t|$ for a real 300\,mm move & 135--166\,mm & \textbf{213.7\,mm} & \\
$z$ direction & wrong & \textbf{correct} & \\
Response & 45--55\,\% & \textbf{71.2\,\%} & \\
\bottomrule
\end{tabular}
\end{center}

\textbf{Read precisely, not rounded up.} 71.2\,\% is real and correctly
signed, not 100\,\%. The remaining gap is not mysterious: this camera's own
intrinsics have been on record as ``approximate\ldots should be calibrated
again later'' since Section~\ref{sec:ros2-realcam} was written, and
calibrating a target that wasn't being tracked at all would have been
pointless until today. That reason no longer holds.

\subsection{Correspondence-sort instability --- confirmed, still open}

Separately confirmed by the same instrumentation and \textbf{deliberately not
fixed in the same change}: the target sort picks its reference edge by
comparing \textbf{unit bearing vectors} --- an angular comparison as seen
from the camera, not the beacon's fixed real-world dimensions. A synthetic
geometry placed at the exact angular near-tie ($\theta^*=58.95^\circ$, located
by bisection, the two separations equal to $-1.4\times10^{-17}$) and run for
1000 trials at $\pm1$\,px of noise selected \textbf{five distinct point-pair
groups} and produced \textbf{134 outright sort failures} --- the synthetic
reproduction of the \texttt{Failed to sort targets using tetrahedron
geometry} messages seen on real frames, and of the 8-cluster result measured
live above. Its effect on the pose, at the specific synthetic near-tie
tested, is \textbf{centimetres}, against the metres BUG-132 caused --- but
the live 60\,cm result above shows the \emph{practical} unstable zone is
wider than that one synthetic point, wide enough to catch an arbitrarily
chosen real measurement distance. \textbf{Warm-starting (above) mitigates
this for continuous tracking} (a solve seeded from a good neighbour is far
less likely to jump to a different assignment's basin than one starting
fixed every frame) \textbf{but this is inference from the mechanism, not
measured directly} --- the sort itself is unchanged, and re-acquiring a lost
beacon with no prior available is still exposed to it.

This harness produced the synthetic numbers above:

\texttt{carolus\_ros2/test/instrument\_p4p\_sort.cpp}

It needs no ROS, no \texttt{colcon}, no camera and no beacon:

\begin{lstlisting}[style=shell]

    carolus_ros2/test/instrument_p4p_sort.cpp \

\subsection{A candidate fix --- and why it is NOT recommended yet}
\label{sec:multihyp}

\texttt{SortTargetsUsingTetrahedronGeometry} never sees \texttt{known\_points}
--- it picks its P1/P2 pair by the single \textbf{largest} pairwise
separation among the four candidates, whatever space it's given (angular,
for the production caller). \textbf{The candidate fix: stop guessing, let
the solver decide.} Generate all 6 possible labelings, solve the real P4P
cost function for each, keep whichever has the lowest \texttt{final\_cost}.

\textbf{Verified synthetically at the identical near-tie geometry, 1000
trials:}

\begin{center}

\textbf{Max} $|$solved $-$ truth$|$ & \textbf{37.4\,cm} & \textbf{5.8\,cm} \\

\bottomrule
\end{tabular}
\end{center}

\textbf{This table is one point, and testing only one point turned out to be
misleading.} A wider sweep (below) found this near-tie sits right at the
boundary of a genuine regression band --- the improvement above does not
generalise the way it looks here.
\end{warningbox}

\textbf{A sweep across viewing angle, 5\textdegree--85\textdegree{} in

\subsection{Why those three regimes exist --- the sort has a hard geometric
limit at \texorpdfstring{$\sim$}{~}58\textdegree}
\label{sec:sortlimit}

Measured 2026-08-27 with \texttt{carolus\_ros2/test/}\allowbreak
\texttt{instrument\_sort\_input\_scale.cpp}, and confirmed independently in
closed form with no noise at all.

The sort's founding assumption is that \textbf{the longest \emph{projected}
edge is P1--P2}. That assumption expires. P1--P2 is 0.1650\,m along $X$ and
foreshortens as the beacon rotates about $Y$; P3--P4 is 0.0909\,m in the
$YZ$ plane and barely changes. Their projected lengths cross over:

\begin{center}
\begin{tabular}{@{}lll@{}}
\toprule
Viewing angle & P1--P2 projected & P3--P4 projected \\
\midrule
55\textdegree & 0.1365 & 0.1202 \\
\textbf{$\sim$58\textdegree} & \multicolumn{2}{l}{\textbf{crossover --- equal}} \\
60\textdegree & 0.1191 & \textbf{0.1222} \\
85\textdegree & 0.0208 & \textbf{0.1294} \\
\bottomrule
\end{tabular}
\end{center}

How often the sort picks the genuinely correct pair, 200 trials per angle:

\begin{center}
\begin{tabular}{@{}ll@{}}
\toprule
Viewing angle & Correct pair chosen \\
\midrule
5\textdegree--55\textdegree & \textbf{200/200} \\
60\textdegree & 16/200 \\
65\textdegree--85\textdegree & \textbf{0/200} \\
\bottomrule
\end{tabular}
\end{center}

\begin{warningbox}
\textbf{Past $\sim$58\textdegree{} the sort is not unstable --- it is
deterministically wrong}, on every frame, and no amount of averaging or
filtering recovers from that. \textbf{Measured operating envelope for this
beacon geometry: reliable below $\sim$55\textdegree{} of viewing angle,
unusable above $\sim$60\textdegree.} Keep the beacon within that cone. A
different beacon changes the crossover angle: it is set by the ratio of the
P1--P2 and P3--P4 edge lengths, so recompute it if the geometry changes.
\end{warningbox}

This also settles what the 58.95\textdegree{} ``near-tie'' in the previous
section actually was --- not an arbitrary awkward geometry, but this exact
crossover, the one angle where the two projected lengths are equal. And it
explains the three regimes directly: below 55\textdegree{} the baseline is
already right every time, so a 6-way search can only lose; above
60\textdegree{} it is always wrong, so a 6-way search can only win.

\textbf{A tempting explanation that was tested and is false.} The ROS2 node
feeds the sort \texttt{.normalized()} unit bearing vectors, while the ROS1
node's production path feeds pixel-scale coordinates --- so the ROS2 port
appeared to have introduced the problem by making the sort compare
\emph{angular} rather than \emph{image-plane} separations. Measured
directly, with the noise drawn once and both representations derived from
it: the two pick the same pair in \textbf{3395 of 3400 trials}, and the
failure band is identical in both. \textbf{The representation is not the
cause.} Recorded because it is the first thing anyone comparing the two
nodes will suspect.

\textbf{The 60\textdegree--85\textdegree{} finding stands on its own,
independent of any fix.} Baseline --- current production --- drops roughly
half its frames outright at steep viewing angles. This may explain some of
the \texttt{Failed to sort targets using tetrahedron geometry} messages seen
interleaved with successful detections across every real-hardware session to
date.

Wired in as \texttt{-p multi\_hypothesis\_sort:=true}, \textbf{default
\texttt{false}}. \texttt{pose\_est.cpp} itself is untouched; the alternative
labeling and 6-way solve live entirely in \texttt{carolus\_node\_ros2.cpp},
reusing \texttt{FindP1P2Indices} (now declared in \texttt{pose\_est.hpp}, a
zero-behaviour-change addition) rather than reimplementing it.

\textbf{Next step is code, not hardware.} With the crossover above
identified, the productive direction is choosing the reference edge from the
known 3D geometry rather than from observed 2D lengths --- not a 6-way
search. No such fix is written yet.

Three harnesses produced the results above, all in
\texttt{carolus\_ros2/test/}:

\begin{itemize}
\item \texttt{instrument\_multi\_hypothesis\_sort.cpp} --- the single-point table
\item \texttt{instrument\_multi\_hypothesis\_sweep.cpp} --- the angle sweep
\item \texttt{instrument\_sort\_input\_scale.cpp} --- the representation test and
  the \texttt{argmax\_ok} diagnostic behind Section~\ref{sec:sortlimit}. Run it
  with \texttt{-{}-verify-baseline} to re-derive the sweep's own numbers from
  the same seeds first; it exits non-zero if they have drifted, so a diverged
  harness cannot pass its output off as a comparison.
\end{itemize}

Same build recipe as \texttt{instrument\_p4p\_sort.cpp} above, substituting
the filename and dropping \texttt{ceresP4P.cpp} from the sources --- neither
harness needs it, since both implement their own corrected cost function
directly.

The live hardware measurements above used
\texttt{carolus\_ros2/test/capture\_pose\_stats.py} (\texttt{/pose} capture
with cluster grouping) and, for beacon LED intensity tuning on a
not-previously-characterised rig,
\texttt{carolus\_ros2/test/beacon\_brightness\_live\_ros2.py} --- deliberately
without a fixed saturated-pixel target band, since that number does not
transfer between different beacons/cameras (this rig runs healthily at
\emph{zero} saturated pixels, tuned instead by watching the detection rate).

\subsection{The mechanism, as first identified by reading the code}

Two facts, each confirmed by reading the relevant source in full rather
than inferred: \texttt{ceresP4P.cpp} solves \emph{every} frame from the
identical fixed starting vector
\texttt{\{0.000, 0.000, -0.001, 0.0, 0.0, 0.7\}} --- no warm start from the
previous pose, nothing carries state between frames. And
\texttt{pose\_est.cpp}'s target-correspondence sort, which decides which
detected blob maps to which of the beacon's four known points, picks its
reference edge by comparing \textbf{unit bearing vectors}
(\texttt{carolus\_node\_ros2.cpp}: each point is built as
\texttt{Eigen::Vector3d(p.x, p.y, 1.0).normalized()}) --- an angular
comparison as seen from the camera, not the beacon's fixed real-world
dimensions. The beacon's true longest edge has no guaranteed angular
advantage at an arbitrary viewing angle, so ordinary measurement noise on
the blob centroids can flip which edge looks longest and change the whole
point assignment fed to the solver.

\textbf{Together, these predict every symptom observed so far, on two
boards and three physical beacons, without a second explanation needed for
any of them:} a correspondence assignment that flips between a small
number of discrete states under ordinary noise, each solved from the same
fixed start with no memory of the last good solve, each settling into its
own repeatable wrong local minimum --- discrete pose clusters rather than
continuous jitter, a \texttt{max distance} diagnostic cycling through a
small repeating set of values, near-zero response to a real displacement,
and outright sort failures when the angular near-tie is too close to
resolve.

\begin{warningbox}
\textbf{This mechanism was already half on record}, in a dated 2026-08-13
comment in \texttt{ceresP4P.cpp} naming the fixed-initial-guess risk and
citing an independent report of the identical line producing curved tracks
in another integration of this same inherited node.

\textbf{The instrumentation it called for was then built and run
(Section~\ref{sec:bug132}), and it changed the conclusion.} The sort flip is
real and confirmed --- but it costs centimetres, and the fixed initial guess
was not what made the pose useless. Holding both unchanged and fixing only
the residual's units took the solved pose from 11.40\,m of error to 0.021\,m.
Kept here because the reasoning above is sound and the two defects it names
are both genuine; corrected here because it identified the wrong one as
dominant. Warm-starting the solver remains a worthwhile, separate change
with its own before/after measurement still owed.
\end{warningbox}
